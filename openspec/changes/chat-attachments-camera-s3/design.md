# Design

## Context

See [proposal.md](proposal.md) for the outcome and confirmed decisions. This design is based on checkout `260b1eef413dc3e6295ef9776c2a5ea868a8ef0f` plus the current uncommitted mobile redesign. Phase 2 now has a bounded implementation and execution evidence; later feature sections remain delivery design, not implementation or benchmark evidence.

Observed integration points:

- `packages/protocol/index.ts`: strict `message.send` carries text, task references and mentions, but no files. `packages/client-core/session.ts` owns reliable delivery and chat lifecycle.
- `apps/mobile/App.tsx` and `ScreenChrome.tsx`: the new paperclip opens a task-only context sheet. `apps/mobile/meeting-device.ts` already uses `expo-document-picker` for audio; general attachment ownership must remain separate.
- `apps/server-admin/web/app/chat-next/chat-next-page.tsx`: web draft ownership, message submission and edit/retry behavior. Web drafts currently live only in memory.
- `apps/server-integrations/mastra-model.ts`: user content explicitly rejects non-text parts. `models.ts` uses string message content; `packages/protocol/service-catalog.ts` has audio capabilities, but no image capability.
- `apps/server-identity/inference-budget.ts`: input estimates use serialized UTF-8 bytes. Base64 image size must not be mistaken for image token accounting.
- `apps/fixture-server/storage.ts` and `model-service.ts` currently participate in shared chat deletion; identity/Mastra code supplies production execution. Coordinate with `niar-240-remove-fixture-interpreter`; do not create a new fixture-only attachment path.
- `Dockerfile`, `compose.yml`, `compose.dokploy.yml`, `scripts/backup.mjs`: one application image/data directory, optional diarizer. External attachment objects change the documented backup boundary.
- `packages/protocol/server-settings.ts` explicitly excludes secrets from settings exports. Initial S3 configuration belongs to operator startup configuration, not member/workspace settings.

## Goals / Non-Goals

**Goals:** one attachment contract and storage adapter for mobile/web; private originals retained across devices; reusable FOSS conversion; photographs retain visual meaning; explicit CRM writes; independently testable storage/conversion/UI checkpoints.

**Non-goals:** an S3 administration product, automatically provisioning hosted accounts, changing existing meeting retention/storage, generic file execution, or adding a second agent/action engine. The complete scope is in the proposal.

## Decisions

### 1. One server-owned S3 adapter

Use the modular AWS SDK for JavaScript S3 client behind a narrow server-only interface: put, head, read/range and delete. Application code passes an internal object handle; it never accepts an arbitrary bucket/key/URL from a member. Use SigV4 with an explicit endpoint/region and selectable path-style or virtual-host addressing. Avoid AWS-specific ownership controls, bucket ACL calls, KMS, object tagging, accelerated endpoints and POST form uploads in the baseline.

The phase-2 contract below is the concrete resolution of C1, R1/R2 and K1/K2 from the independent design review. It cleared fresh pre-implementation review, and the bounded implementation is independently accepted in [storage-final-review.md](reviews/storage-final-review.md); NIAR-250 tracks tasks 2.1–2.4. It does not resolve the later ingestion/conversion findings.

#### Phase 2 configuration and startup contract (C1/K2)

`apps/server-storage/config.ts` owns `StorageConfiguration = disabled | invalid | configured`. It reads only operator environment and mounted secret files, separately from the strict `ServerConfigSchema` and ordinary settings. No nonempty `NIARO_S3_*` setting means `disabled`; any nonempty setting opts into validation, including an unknown name (unknown names are invalid). Empty/whitespace environment values count as absent. Configured invalid storage never disables ordinary text chat.

| Setting | Exact accepted value / default |
| --- | --- |
| `NIARO_S3_ENDPOINT` | Optional HTTP(S) service origin, no userinfo, path other than `/`, query or fragment; absent means the AWS regional origin `https://s3.<region>.amazonaws.com` |
| `NIARO_S3_REGION` | Required, lowercase signing-region token, 1–63 characters, letters/digits/hyphens |
| `NIARO_S3_BUCKET` | Required DNS-style lowercase bucket, 3–63 characters; no IP literals, ARNs or access points |
| `NIARO_S3_PREFIX` | Default `attachments`; 1–256 characters of slash-separated `[A-Za-z0-9_-]+` segments; no empty/dot/encoded segments, leading or trailing slash |
| `NIARO_S3_FORCE_PATH_STYLE` | Exactly `true` or `false`, default `false` |
| `NIARO_S3_CREDENTIAL_MODE` | Required, exactly `static` or `default` |
| `NIARO_S3_ACCESS_KEY_ID`, `NIARO_S3_SECRET_ACCESS_KEY`, `NIARO_S3_SESSION_TOKEN` | Static mode requires the first two; token optional; bounded, nonempty secret values without control characters |
| `NIARO_S3_ACCESS_KEY_ID_FILE`, `NIARO_S3_SECRET_ACCESS_KEY_FILE`, `NIARO_S3_SESSION_TOKEN_FILE` | Exact file alternatives to those values; supplying both nonempty variants is invalid, never precedence-based |
| `NIARO_S3_ALLOW_HTTP` | Exactly `true` or `false`, default `false`; valid only for a private/loopback HTTP endpoint |

Read secret files synchronously once per process/configuration load, maximum 16 KiB each, regular files only; remove one trailing LF or CRLF, reject remaining control characters/empty contents. File paths and contents never appear in errors. Rotation requires restart or rerunning the explicit command; no watcher or ambient fallback. `default` rejects all Niaro static secret variants, explicitly uses the SDK default credential chain, and resolves it only during a network operation. The offline checker neither resolves credentials nor DNS nor instance metadata.

HTTPS always verifies certificates via Node trust (including operator `NODE_EXTRA_CA_CERTS`); configured S3 with `NODE_TLS_REJECT_UNAUTHORIZED=0` is invalid. HTTP requires explicit opt-in and every connected address must be loopback, RFC1918 IPv4 or IPv6 ULA. Reject public/link-local/multicast/unspecified addresses and IPv4-mapped bypasses. Validate IP literals offline; resolve names at the actual socket lookup and reject the complete answer set if any address is public. Use the validated lookup result for that socket so DNS cannot be checked once then rebound on a second lookup. Disable SDK region/endpoint redirects and use a transport which never follows HTTP redirects. Disable SDK host rewriting other than the selected bucket addressing; private named HTTP uses path style so the validated endpoint is the actual host. No custom endpoint discovery or provider fallback.

`loadStorageConfiguration()` returns only safe `{state: "invalid", code, field?}` diagnostics on error, or a server-private config object. Raw SDK messages, response bodies, endpoint strings, credential objects and secret file paths do not enter logs/JSON/errors. `server:check`/`niaro check` validates this result after ordinary profile validation, reports `disabled`/`configured` separately, exits nonzero for invalid storage, and makes no network calls or DB changes. Successful offline checking means syntax/secret presence only.

`createReferenceServer()` passes the configuration to the shared production workflow storage initialization through `createFixtureServer()`; it does not expose S3 in protocol/member/admin settings. `FixtureStorage.initializeObjectStorage()` runs the location guard on its own opened workflow DB before any storage service can be returned. Invalid config, location refusal, or later operation failure gives an unavailable storage runtime with a safe operator code, while the HTTP/text server continues. Startup does not probe the network or claim readiness; state `configured` means locally admissible, not verified connectivity. `server:storage-check`/`niaro storage-check` is the distinct, explicit network contract command. No attachment routes, model capability or serving activation is added in phase 2.

#### Phase 2 persistence and interface contract (R1)

Use the existing `workflow/workflow.sqlite` (or the profile's workflow `dataDirectory/workflow.sqlite`) opened by `FixtureStorage`, not identity DB or a second detached DB. This is an additive module-owned migration inside the existing workflow initialization transaction; preserve `user_version=1` and old text data. `apps/server-storage/registry.ts` creates `object_storage_locations(id TEXT PRIMARY KEY, descriptor TEXT NOT NULL)`, `object_storage_active(slot INTEGER PRIMARY KEY CHECK(slot=1), location_id TEXT REFERENCES object_storage_locations)`, and `object_storage_objects(id TEXT PRIMARY KEY, location_id TEXT REFERENCES object_storage_locations, object_key TEXT UNIQUE, owner TEXT, sha256 TEXT, size INTEGER, state TEXT CHECK(state IN ('reserved','retained','deleting','deleted')), mutation TEXT CHECK(mutation IN ('idle','put','delete')), mutation_id TEXT, write_uncertain INTEGER CHECK(write_uncertain IN (0,1)))`, with strict tables and non-null/check constraints. These records contain no credentials or source filenames. Descriptors contain only normalized endpoint, region, bucket, prefix and addressing mode. Location ID is SHA-256 of a versioned deterministic JSON tuple of those fields; changing credentials/HTTP permission leaves identity unchanged.

The registry's synchronous `activate(config)` transaction preserves the active location on rejection. Same identity succeeds; a different identity succeeds only when no non-deleted object reservation/reference remains for the previous location. Reservations count immediately, including unknown upload outcomes and pending deletes, so a network loss cannot permit replacement. Disabling or invalidating configuration retains every row and does not forget the location. Before each durable operation the registry checks the current active identity; stale runtime instances cannot write after an allowed switch. No operator override/migration/reset command is provided. Later attachment bindings and cleanup jobs must join this same workflow transaction boundary and retain the registry reference until confirmed deletion; phase-3 schema/acceptance work remains explicitly pending.

**Same-handle mutation admission and unknown outcomes (SR1):** Registry rows initially have `state=reserved`, `mutation=idle`, `mutation_id=NULL`, `write_uncertain=0`. Before network I/O, `beginPut(handle)` atomically checks the active location and immutable row, requires state reserved/retained, no uncertainty and idle mutation, then commits `mutation=put` and a fresh operation UUID. `beginDelete(handle)` commits state deleting and its delete operation UUID only from idle, without write uncertainty. Deleting is irreversible: no later put is admissible, including after a failed/unknown delete. Reservation creation may join the enclosing workflow transaction. Mutation admission and completion require their own committed transaction and return `busy` if an outer transaction is already open; callers must commit reservations before beginning I/O. A simultaneous mutation returns `busy` immediately; it never queues. The persisted compare-and-set admission applies across multiple wrappers using the same DB; the process-local two-transfer cap is additional. A deleted handle's repeat delete returns locally without I/O and can never create another object.

A successful put's matching post-I/O transaction checks location, state and the operation UUID, sets retained/idle and clears the UUID. A known refusal clears only that operation's mutation, retaining its reservation. A successful DELETE plus missing HEAD may mark deleted/idle only when that operation owns the row and there was no admitted/unresolved PUT. Post-I/O token/location checks cannot restore a deleting/deleted row, clear another operation's admission, or rewrite an old location. They do not pretend to undo a remote late write.

An unconfirmed dispatched PUT is different from a failed verification read after a confirmed PUT response. If the PUT response was lost/timed out or its dispatch outcome is otherwise unknown, commit `write_uncertain=1`, retain the reservation, and clear its mutation token only by matching operation UUID. All further same-handle mutations, including DELETE, fail closed with `uncertain` and `retryable=false`; reads may report the object but neither a missing HEAD nor a subsequent successful conditional request proves the earlier remote PUT has settled. Phase 2 intentionally provides no command that clears this quarantine or releases its location. Provider-specific reconciliation/migration proof is a later explicit operator design; report the retained uncertainty honestly. If PUT returned a confirmed success but independent read-back failed, the write is settled: retain the reservation and clear admission, allowing explicit verification/retry or delete. Known SDK/service failure responses are settled refusals; raw network/timeout failures before a conclusive response are conservative unknown outcomes.

For a DELETE with unknown outcome, keep state deleting and the location reference; no PUT can ever reuse the handle. After clearing only its own admission, an explicit repeated delete may confirm deletion and absence. A late earlier DELETE cannot recreate data and cannot target a new key/location. On workflow startup after acquiring the existing owner lock, recover persisted interrupted put admissions as `write_uncertain=1` and retain them; interrupted deletes remain deleting and become eligible only for explicit delete retry. This recovery is run once by the owning `FixtureStorage` initialization, not by constructing arbitrary secondary registry wrappers. Closing storage aborts outstanding local requests and leaves durable admissions for recovery; it does not claim remote cancellation erases uncertainty.

Production tests pause a PUT after durable admission, assert DELETE is busy and location activation is migration-required, then release PUT and verify explicit delete can finish before switching. A separate lost-response case accepts the remote PUT while returning uncertainty, verifies that DELETE and location replacement remain refused even when HEAD is missing, and proves a delayed remote write cannot make the registry forget its retained location. Reopen the workflow DB with a persisted in-flight PUT and prove the same quarantine. Exercise two wrappers against one registry, delete uncertainty/retry, and post-I/O token rejection; these are phase-2 invariants, independent of later chat tombstones and cleanup workers.

`apps/server-storage/types.ts` defines readonly internal `ObjectHandle {version: 1, id, locationId, key, owner, sha256, size}` and safe `StorageError {code, retryable, outcome}`. IDs are UUIDs; owner is a server-issued opaque UUID (future attachment scope mapping stays server-side). Keys are `<prefix>/objects/<sha256(owner)>/<uuid>`. Handles are frozen on creation, never accepted from client input, and each operation checks the location, key derivation, bounded integer size and lowercase SHA-256. All production handles are reloaded/compared against registry records; changing a copied handle is rejected. A deleted handle cannot be put again.

`S3ObjectStore` implements `put(handle, Uint8Array): Promise<"created" | "already-present">`, `head(handle): Promise<{size, sha256}>`, `get(handle): Promise<Uint8Array>`, `range(handle, {start,end}): Promise<Uint8Array>` (inclusive bounds), and `delete(handle): Promise<void>`. `RegisteredObjectStore.reserve(owner, {sha256,size})` commits the reservation before I/O and returns a handle; the wrapper is the production entry point. This checkpoint intentionally uses bounded buffers, maximum 25 MiB per object, at most two active operations per store; reject excess work with `busy` instead of unbounded queues. Requests have 5-second connect, 30-second total operation including response consumption and credential resolution, no automatic SDK retries; cancellation destroys the body/socket as appropriate. Public abort/cancel transfer APIs remain phase 3.

Put independently hashes actual bytes and rejects size/digest mismatch before I/O. Always send `If-None-Match: *`, `ContentLength`, metadata SHA-256, and SDK checksums only when required for compatibility. A successful new put is confirmed by an independent whole-object read with matching size/hash before returning `created`. A 412 is not success by metadata alone: read/hash the existing object and return `already-present` only for identical bytes. Reusing the handle with changed bytes conflicts. Whole get streams into a bounded buffer and independently verifies length/SHA-256 (ETag is opaque); head verifies declared size and digest metadata but is not proof of byte integrity. Range verifies exact status/content-range/length and bounds; a range alone cannot prove whole-object SHA-256 and must not claim it. Unexpected non-null version IDs on any operation refuse the erasure contract. Delete is repeat-safe, checks bucket erasure prerequisites before deletion, treats a missing object as success, and marks `deleted` only after successful delete plus missing head; unknown/network outcomes keep the durable reference. There is no automatic upload retry on uncertainty.

Codes are `invalid_config`, `unavailable`, `denied`, `not_found`, `conflict`, `integrity`, `location_mismatch`, `migration_required`, `bucket_not_erasable`, `invalid_handle`, `busy`, `timeout`, `uncertain`, `probe_failed`, `cleanup_failed`; only unavailable/network/timeouts/busy are retryable when the handle has no unresolved PUT; quarantined mutation uncertainty is explicitly not retryable. Outcome is `not_started`, `confirmed` or `unknown`; network failures after mutation dispatch are `unknown`. All thrown external details are discarded. Contract tests assert no secret/reflected service payload reaches the operator JSON or errors.

`apps/server-storage/probe.ts` exports `checkStorageContract(config)`. It checks GetBucketVersioning (neither Enabled nor Suspended permitted) and GetObjectLockConfiguration (only documented `ObjectLockConfigurationNotFoundError`/`NoSuchObjectLockConfiguration` with HTTP 404 is an absent setting; access denied/unknown APIs fail closed), then uses random handles under the configured prefix for conditional put/unchanged retry/refused changed retry, head, hash-verified whole read, exact range, missing read, anonymous GET refusal and repeat delete. Anonymous access uses the same bounded/private validating transport without credentials; redirects fail. Probes never change bucket policies, versioning, retention or production registry activation. Cleanup runs in `finally`, returns a separate safe cleanup result, and fails the command if any probe object cannot be confirmed absent. A unique synthetic conflict object may be written using the low-level client within the probe to test that conditional writes actually refuse replacement; always include it in cleanup. The command opens no live workflow DB and explicitly reports that location acceptance is a startup/registry concern.

**Alternative:** direct browser/mobile presigned transfers. Defer: proxying bounded uploads/downloads through Niaro avoids CORS, public/internal endpoint splitting and bearer URLs that remain usable after chat deletion. It costs server bandwidth, acceptable for the proposed first limits.

### 2. RustFS locally, Hetzner hosted, the same contract everywhere

Add opt-in `object-storage` services to both Compose files. Pin `rustfs/rustfs:1.0.4@sha256:ed9210d6411d77ffceb70d94b964a3cb7d225983368bc25bebe01e995293dcc2`. RustFS owns a separate named volume at `/data`; Niaro's single local data directory still contains its DB/metadata, never remote object bytes. No MinIO tool or image. A single-disk RustFS instance is not redundant storage.

#### Bootstrap and readiness (R2)

The `rustfs` service uses required, non-default `NIARO_RUSTFS_ROOT_ACCESS_KEY` and `NIARO_RUSTFS_ROOT_SECRET_KEY`, injected only into RustFS and one-shot `rustfs-bootstrap`, never into the Niaro service. Empty/unset Compose interpolation does not prevent default/external-S3 config; enabled RustFS fails closed without valid secrets. Bootstrap accepts separate `NIARO_S3_ACCESS_KEY_ID`/`SECRET_ACCESS_KEY` (or mounted `_FILE` alternatives), static mode, configured bucket/prefix and `us-east-1` region. Reject common defaults, short secrets, root/application equality and application session tokens. The application key is operator-supplied and stable across reruns; do not generate or print it. Mounted secrets remain the recommended production alternative to Compose env; secret-file mounts must be declared by the operator in an override and the exact in-container paths set.

`apps/server-storage/bootstrap.ts` and `scripts/storage-bootstrap.ts` run in the Niaro application image (same pinned SDK), exposed as `niaro storage-bootstrap` and `npm run server:storage-bootstrap`. Wait with bounded retries (up to 60 seconds) for RustFS using root HeadBucket/CreateBucket; create only the named bucket, treating already-owned as success only after verifying access/properties. Refuse versioning, Object Lock, public anonymous probe access and unexpected errors; never change erasure settings on an existing bucket. Provision the application principal using RustFS 1.0.4's SigV4-signed JSON `PUT /rustfs/admin/v3/add-service-account`, with explicit requested key/secret and restricted inline policy. Bucket permissions: `GetBucketVersioning`, `GetBucketObjectLockConfiguration`, `GetBucketLocation` on the configured bucket; object `PutObject`, `GetObject`, `DeleteObject` only on `<bucket>/<prefix>/*`; no bucket creation, IAM/admin, policy mutation, ListAllMyBuckets or foreign namespace. The bootstrap credential is the parent/admin account; its authority is never the application authority.

On a rerun first verify the supplied application credentials and same contract. If that succeeds, verify the existing service-account policy via signed admin inspection and require it to equal the expected scope; do not silently adopt broader permissions. If absent, create, then inspect and run the application contract. If the key exists but secret/policy differs, fail with a safe conflict; do not rotate, broaden, delete or print credentials automatically. An uncertain create is recovered only by inspecting/verifying that same requested principal on the next explicit rerun. This RustFS admin endpoint is bootstrap-only, never an application adapter feature or a hosted-S3 requirement. Inspection is SigV4-signed `GET /rustfs/admin/v3/info-service-account?accessKey=<requested key>`; require HTTP 200, `accountStatus` enabled/on, `impliedPolicy=false` and a parseable JSON-string `policy` equal to the expected statement set. The isolated pinned-image pilot returned HTTP 200 with `parentUser`, `accountStatus`, `impliedPolicy=false` and string `policy` on 2026-10-30; this verifies inspection feasibility, not the future production bootstrap. An absent principal is only the documented no-such-account response; other errors fail closed.

`rustfs-bootstrap` depends on RustFS `service_started` and implements the bounded readiness wait itself (no unverified in-image curl dependency). It exits nonzero on readiness, credentials, policy, erasure, probe or cleanup failure; `restart: "no"`. No Niaro `depends_on` ties external-S3 installs to the optional profile. Startup is two explicit commands: first `docker compose --profile object-storage run --rm rustfs-bootstrap`, then `docker compose --profile object-storage up -d niaro` (plus selected HTTPS/other profiles). A combined `up` may run text chat before bootstrap; it must not be documented as storage-ready. The application never uses admin credentials or root fallback while bootstrap is incomplete. Readiness is established by the explicit application-credential contract probe, not by a TCP healthcheck or a running container. Re-running bootstrap is safe after restart/recreation and must not modify existing objects.

RustFS connects only to the project default network, never Dokploy's external proxy network. Publish only the API on loopback for local development (`127.0.0.1`, configurable host port); the Dokploy file publishes no storage ports. Disable the console by default; an operator may explicitly enable it with a loopback-only override. Document setting the application's S3 endpoint to `http://rustfs:9000`, path style and private HTTP opt-in, or an external HTTPS origin without selecting the profile.

### 3. Bounded server ownership and acceptance checkpoint (A3–A5)

This section and decision 7 specify the **next server checkpoint**, on the refreshed, independently accepted phase-2 storage foundation (tasks 2.1–2.4). They are proposed behavior, not current code. Deliver strict protocol/HTTP schemas, workflow persistence, bounded upload/download, message acceptance, lifecycle recovery and tests through the real account/native integration. Stop before converters, multimodal hydration, camera/composer UI and CRM proposal implementation. Keep attachments disabled by default (`NIARO_ATTACHMENTS_ENABLED=false`); capability-aware integration clients can exercise retention-only acceptance with `processingAvailable=false`. Such acceptance reports `blocked_capability`, retains the original and makes **no model call**, including on the caption alone. General client activation remains a later integrated checkpoint. Storage configuration/probe success alone does not advertise extraction or image understanding.

#### 3.1 Actual production seam and ownership

`apps/fixture-server/http.ts` is the HTTP entry used by `apps/reference-server/runtime.ts`, including account sessions through `IdentityService`; its directory name is not evidence of a separate demo-only path. It validates host/origin, authenticates a workspace bearer/browser bridge, and revalidates the captured actor via `run` after body reads and before mutations. Extend that path, with `apps/server-identity/service.ts` providing passive attachment access without loading model credentials. Account scopes use the existing stable `account-<workspace>` connection identity; use the complete validated `Scope` key (connection/server/user/workspace), never a client-supplied owner or device ID. Per-person aggregate admission uses `(serverId,workspaceId,userId)`, shared by web/mobile credentials. The legacy fixture principal is test coverage only; production routes require current account membership and existing read/write permissions. Workspace/instance administration does not grant access to another person's originals.

The workflow DB and owner lock are in `apps/fixture-server/storage.ts`: WAL/FULL SQLite, short synchronous `BEGIN IMMEDIATE` writes, additive module migrations retaining `user_version=1`. `ConversationHistory` stores full public history independently of the bounded live workflow projection. Put all attachment metadata, acceptance receipts, registry references and cleanup outbox records in **this same workflow connection/transaction**; no second attachment DB and no SQL transaction across object/network I/O. The identity DB (`identity/identity.sqlite`), catalog native-turn/action/budget records and the native LibSQL checkpoint/memory store (`ServiceCatalogStore.nativeStorageUrl` (`identity/identity.sqlite.mastra.sqlite`), `apps/server-agent/runtime.ts`) remain separately owned; cross-store atomic commit is unavailable.

Separate immutable content from selections and bindings:

| Record (new strict workflow tables) | Keys, constraints and responsibility |
| --- | --- |
| `attachment_generations` | `(scope_key,generation_id)` PK, UUID generation; conversation ID, state `reserved/live/archived/tombstoned`, predecessor generation nullable. One live generation per scope/conversation and one unadopted current-mode reservation per scope/unsaved conversation (partial unique indexes). Current-mode drafts for that unsaved ID share its reservation; the existing create command adopts it deterministically. Content ownership epoch, distinct from native conversation-session/thread generation. Add lazily for existing chats; old text data stays readable. |
| `attachment_drafts` | server UUID PK, scope, target conversation, expected current generation nullable, target generation FK, mode `current/new`, revision positive, state `open/consumed/removed/expired`, created/absolute expiry, accepted command nullable. No unsaved chat is created by making a draft. |
| `attachment_contents` | server UUID PK, scope/generation FK, registry handle FK unique, immutable safe filename, declared/detected MIME, positive size and SHA-256, lifecycle `staging/available/tombstoned/purged`, transfer state below, operation token nullable, creation/expiry. Original byte descriptor never changes after creation. No global digest deduplication; equal bytes in different generations get different handles/keys. |
| `attachment_draft_items` | `(draft_id,content_id)` PK, unique `(draft_id,ordinal)` with ordinals 0–9, source binding nullable, `active/removed`; generation equality enforced in the transaction. Pins content only while the draft is open and unexpired. |
| `attachment_bindings` | `(scope_key,message_id,content_id)` PK, unique message ordinal 0–9, generation FK, accepted command, state `live/tombstoned`. | `attachment_ingestions` | UUID PK; unique `(scope_key,logical_message_id)`; generation, visible user message ID, immutable ordered content set and intent digest; state below, version, createdAt. One logical request survives deliberate native retries; Again creates another logical request. |
| `attachment_attempts` | UUID PK; ingestion FK, command/idempotency IDs unique per scope, immutable request hash, ordinal unique per ingestion, state, accepting boot/task epoch, local processing version nonnegative, handoff UUID nullable (once admitted it is never cleared), sealed pre-dispatch proof ID nullable, native command/root references nullable, safe failure code, timestamps. The command receipt and attempt are committed together. The logical ingestion state is projected from its current attempt; both state/version updates occur in the same workflow transaction. | `attachment_mutations` | `(scope_key,request_id)` PK; route/target and canonical request hash, minimal response IDs/revisions. Exact JSON-mutation retries recover their result; a reused ID with other input is `attachment_conflict`. Purge user-bearing payloads with the target, retain content-free rejection tombstones. |
| `attachment_purge_jobs` | UUID PK; unique `(kind,target_id)`, kind `object/native_context/local_spool`, immutable registry handle or native generation/command references; state `pending/running/retry/blocked_uncertain/blocked_policy/done`, operation token, attempts, next time, safe error. No bearer, model input, original filename or extracted document in a job. |

Content transitions are `staging -> available` only after verified storage, then either state may become `tombstoned -> purged`; neither transition can reverse. Versioned local retry can re-enter queued before any handoff; deliberate native retry adds a new attempt rather than resetting unknown. Mark every state edge with the captured generation/version/token checks.

Use explicit NOT NULL/CHECK/FK constraints and indexes on owner/state/expiry/next time; typed schema parsing validates stored JSON and every state transition. Attachment module migrations execute inside `FixtureStorage` initialization, sharing the phase-2 registry connection. Expose an internal synchronous registry reservation-row primitive to the workflow transaction owner: standalone `RegisteredObjectStore.reserve` wraps that same primitive, while attachment create calls it within the already-open workflow transaction, with no nested BEGIN or early commit. The reviewed public reserve/put/head/get/range/delete contract and before-I/O durability remain unchanged. Only reservation joins an outer workflow transaction; remote mutation begin/finish and all asynchronous store I/O must run after that transaction closes, with the accepted registry guarding against mutation inside an outer transaction. Integrate against the final independently reviewed phase-2 implementation, not a provisional sibling checkout. Missing workflow/identity proof fails closed, never repairs ownership by guessing. Content/derivative ownership is generation-scoped; later derivatives have their own registry handle, parent content ID, kind and processor-version/attempt lineage, and inherit the same tombstone. No derivative table/worker is needed to claim this checkpoint complete; decision 7's outbox contract must accept all later lineage handles.

#### 3.2 Exact wire profile and routes

Implement `packages/protocol/attachments.ts` using strict Zod objects and discriminated unions; unknown keys, duplicate query keys, coercions and unsupported profile versions fail. In the notation below every listed field is required unless suffixed `?`; `null` is an explicit value, not omission. `Id` is the existing `[A-Za-z0-9._:-]{1,160}` protocol ID, `Uuid` a canonical lower-case UUID, `Sha` 64 lower-case hex, `Rev` a positive safe integer, `Bytes` a positive safe integer, `Time` UTC ISO date-time. Filenames are NFC, 1–255 UTF-8 bytes, basename-only with slash/backslash/NUL/control/bidi controls rejected. MIME strings are lower-case `type/subtype` ASCII, 1–127 bytes, without parameters. SHA and byte size describe the exact uploaded original, never a decoded image. Every JSON body is at most 8 KiB, except existing commands which remain **65,536 bytes**; file bytes never enter command JSON/base64.

#### 3.3 Capability delivery, reuse and authorization

Chat-directory summaries stay readable with existing fields; selecting an affected chat requires upgrade. Keep all other delivery profiles and their closed query allowlists coherent.

Again/Edit use a fresh draft whose reference items resolve server-side to currently live bindings in the same ownership generation. #### 4.3 Fixed IPC and evidence DTO v1 (G3)

Use one Unix stream socket, one request and one response per connection, **no base64 or multiplexing**. All lengths are unsigned **4-byte big-endian**. Request is `u32(metadataBytes) || strict UTF-8 JSON || raw body || write-half-close`; metadata is 2..4096 bytes, body is exactly job.inputBytes for submit and zero for every control. Receiver must read the declared body **and then read EOF** before launch: an extra byte, including a delayed byte or second frame, rejects the attempt without gate execution. EOF before N is truncated; reaching N without EOF is still pending, never proof of exact input. Idle deadline 15 s and absolute transfer/EOF deadline 120 s apply from accept; cancel closes that transfer. Response is `u32(metadataBytes) || JSON || u32(resultBytes) || result || EOF`; result length is 0 except result-outcome, <=2 MiB, and must equal metadata. Parent verifies response EOF, exact bytes/hash and DTO before observation. Controls likewise require EOF before any control mutation. Keep the response read side open after request half-close. No transport close/timeout implies success.

The following is a literal closed tagged-union schema, with intersections expanded into exactly the listed fields; all fields required, `null` explicit, no other fields. `Uuid` is canonical lowercase UUID (`[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}`), `Sha` 64 lowercase hex, `Rev` 1..2^31-1; `Processor` is the ASCII version token `[A-Za-z0-9][A-Za-z0-9._+-]{0,127}` (whole value, 1..128 bytes). This admits `conversion-v1.fixture`, `0.1.9` and `5.5.0`; angle brackets, ampersand, backslash, quote, slash, whitespace and non-ASCII are rejected everywhere Processor occurs, including Identity, Job and ConversionResultV1. `BootRef={epoch:Epoch,counter:Counter}` uses 4.2a. `Identity={protocol:1,processorVersion:Processor,imageBuildSha:Sha,gatePolicySha:Sha,enginePolicySha:Sha,assetsSha:Sha,probeSuiteSha:Sha,platformSha:Sha,deploymentSha:Sha}`; `Boot=BootRef & {identity:Identity}`. Identity/hash mismatch is unavailable, never negotiated downgrade.

```ts
type Job = { jobId:Uuid; attempt:Rev; generation:Uuid; attemptVersion:Rev;
  contentId:Uuid; sha256:Sha; inputBytes:number; // 1..26_214_400
  format:"pdf"|"docx"|"xlsx"|"pptx"|"csv"|"tsv"|"txt"|"md"|"png"|"jpg";
  processorVersion:Processor; limitsProfile:"conversion-v1" };
type Request =
  | {version:1;op:"status";query:"readiness"}
  | {version:1;op:"status";query:"job";job:Job}
  | {version:1;op:"submit"|"cancel";job:Job}
  | {version:1;op:"ack";job:Job;outcomeSha256:Sha};
type Outcome = {kind:"result";bytes:number;sha256:Sha} // 1..2_097_152
  | {kind:"failure";reason:FailureReason}; // no parser evidence/body
// Every Response has this exact common prefix:
type Base = {version:1;op:"submit"|"status"|"cancel"|"ack"|null;boot:Boot};
type Response = Base & (
  | {kind:"readiness";state:"starting"|"ready"|"running"|"restarting"|"retained"|"unavailable";
     slot:"empty"|"occupied";qualificationKey:Sha|null;probe:BootRef|null;
     reason:"none"|"startup"|"busy"|"restarting"|"qualification_required"|"qualification_failed"|"unavailable";
     retryAfterMs:number|null}
  | {kind:"job";job:Job;state:"receiving"|"running";origin:BootRef;retryAfterMs:number}
  | {kind:"outcome";job:Job;origin:BootRef;outcome:Outcome;outcomeSha256:Sha}
  | {kind:"cancel";job:Job;origin:BootRef;disposition:"requested"|"already_requested"|"terminal"}
  | {kind:"ack";job:Job;disposition:"cleared"|"already_cleared"|"absent"}
  | {kind:"absent";job:Job;disposition:"absent"|"already_acked"}
  | {kind:"error";job:Job|null;code:"invalid_request"|"unsupported_version"|"busy"|"conflict"|
     "restarting"|"unavailable"|"not_terminal"|"not_recycled"|"already_acked";
     retryAfterMs:number|null});
```

Readiness response has op status; all other successful responses echo the request op. Error echoes a recognized op (otherwise null); job is null for an invalid/unparsed descriptor or readiness error, otherwise the validated requested Job. `retryAfterMs` is an integer 1000..10000 only for job pending, readiness starting/running/restarting/retained and busy/restarting errors; otherwise null. Ready requires empty slot, qualified current key, probe from a prior epoch/counter, reason none and null retry; unavailable has reason qualification_failed/unavailable, null retry. Starting uses startup/qualification_required; running uses busy, restarting uses restarting, retained uses busy; all have the corresponding slot (starting may be either, running/restarting/retained occupied). QualificationKey/probe are both null until a matching passed proof exists, then identify its key/origin. Socket/ledger/auth failures that cannot safely construct Base close the connection without a response and remain unavailable.

Valid submit durably reserves a receiving slot before body transfer, checks exact count/EOF/SHA and sniffed format before a running fsync and gate launch; no client-provided resource increase, source name, URL, command, environment or path. A transfer/hash/type failure becomes retained failure malformed (size overflow input_limit; deadline timeout) and recycles without gate launch. Cancel during receiving/running durably marks cancellation, terminates transfer/parser by PID1 exit and retains cancelled; repeated cancel is already_requested, terminal cancel is terminal and does not alter the outcome. Pending job and requested/already_requested cancel responses require origin epoch **and counter equal to the response boot**; prior-boot receiving/running work must already have become terminal interrupted/resource_unknown. Terminal/recycled outcomes keep their original origin, and terminal cancel may refer to it. Every terminal result has origin from receiving/running, even when no parser launched. Result outcome has a validated ConversionResultV1 body (including failed DTOs); supervisor/transport failures use FailureReason = `input_limit|malformed|timeout|cancelled|resource_unknown|interrupted|invalid_result|output_limit|scratch_limit|unavailable`, zero body. `outcomeSha256` is SHA-256 of `["conversion-outcome/1",Job,origin,Outcome]` under the exact rule below. This binds failures as well as result descriptors; result bytes are separately hashed.

**Exact hash bytes (qualification and outcome, IC-1).** Validate the closed typed input first, including duplicate/unknown-key rejection, strict UTF-8, bounded decode and integer/enum/alphabet bounds; reconstruct in the specified order rather than hashing received JSON or iterating a map. Emit only ASCII bytes, no BOM, spaces, line breaks or **trailing newline**. Arrays/objects use literal `[`, `]`, `{`, `}`, comma and colon. Every key/string is enclosed in byte `0x22`; its decoded ASCII characters are emitted literally with **no escaping** (no Unicode, slash or HTML escape sequences). All admitted hash strings are safe: fixed domain/key strings; Processor's token alphabet; lowercase UUID/Sha/Epoch; Job's exact format and limitsProfile enums; Outcome's kind/FailureReason enums. None can contain quote, backslash, control, `<`, `>` or `&`; rejecting those values removes any encoder escape choice. Emit validated integer values as shortest unsigned base-10 digits, no leading zero, decimal point, exponent or sign; the fixed protocol is `1`. Qualification uses exactly the array in 4.2a. Outcome uses Job keys `jobId,attempt,generation,attemptVersion,contentId,sha256,inputBytes,format,processorVersion,limitsProfile`, then origin keys `epoch,counter`, then Outcome keys `kind,bytes,sha256` for result or `kind,reason` for failure. No null/optional/free-text fields enter either hash. Input key order and legal JSON escape spellings do not affect these reconstructed bytes. Hash **those bytes**, not a generic encoder's arbitrary output; Go Encoder.Encode's newline is forbidden. Result body SHA hashes the exact received body bytes without reserialization; its free text is outside these two preimages.

Exact submit replay consumes/verifies its body/EOF, then returns job/outcome without execution; a known last-ACK identity returns error already_acked. Same jobId+attempt with any changed tuple conflicts; a distinct submit while occupied is busy (or restarting during recycle). Job status returns pending job/outcome, or absent/already_acked with no body. Cancel of an unknown/cleared identity returns the same absent variant; a different occupied identity is not cancelled. ACK requires exact Job **and** outcomeSha256, terminal state and a different current epoch/larger counter than origin; mismatch -> conflict, pending -> not_terminal, old epoch -> not_recycled. Matching ACK atomically replaces slot by empty plus one content-free lastAck `{job,outcomeSha256}`; response cleared, repeated same ACK already_cleared. Unknown/evicted ACK returns absent, never proof of prior completion. Status of lastAck returns already_acked; older history is parent-owned. A different occupied job is unaffected; a conflicting tuple for a known jobId+attempt conflicts on every operation. An ACK in the old epoch cannot prevent its exit. Worker retains only the latest ACK marker; the parent's persistent terminal/idempotency history prohibits resubmitting older settled identities.

Only one data connection and four controls; reject excess immediately with busy if framing/auth can safely complete, otherwise close, never queue bodies/promises. Parent polls as 4.4; result collection caps stdout 2 MiB/stderr 64 KiB independently while reading, terminating on overflow, with bounded streaming encoder/validator before allocation. Logs have safe IDs/reasons only. The [hash-byte vectors](reviews/conversion-closure-fix-20261030/hash-vectors.v2.json) include exact preimages and adversarial accepted/rejected inputs for both hashes; their small Go/Node checks prove serialization interoperability only. ## Risks / Trade-offs

- Parser dependencies and OCR RAM -> bounded worker, offline model assets, license/dependency inventory and a measured pilot before selecting the engine.
- Network loss between DB and S3 -> durable staging/deletion records, immutable keys, digest verification and crash tests; no distributed-transaction claim.
- S3 vendor differences -> a documented minimal contract and reusable endpoint tests; Hetzner and RustFS are distinct evidence targets.
- Document prompt injection -> extracted content is untrusted source material, never system instructions or permission; actions keep normal validation/approval.
- Spoofed MIME, oversized decoded images, archive bombs -> inspect actual bytes and enforce independent upload/decoded/page/output limits.
- Attachment storage failure -> text chat remains usable; no fallback to public URLs or a different storage location.
- Multi-device deletion races -> authorization at read/dispatch/commit and immediate metadata tombstones; physical purge is observable and retryable.

## Migration Plan

Add versioned protocol/schema fields and attachment tables without rewriting existing messages. Negotiate attachment metadata so older clients never mistake an attachment-only message for an empty one; unavailable clients receive an upgrade-required response for attachment-bearing histories. Keep text-only behavior unchanged.

Ship storage configuration and isolated RustFS tests first, then upload/lifecycle, conversion/model support and both clients. Enable attachments only after storage and processing capabilities are configured. Update deployment/backup guidance before activation. Existing meeting files stay local. Roll back using coordinated pre-upgrade DB/object backups; do not point an old server at attachment-bearing upgraded data.
