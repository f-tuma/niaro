## Material findings on the initial revision

### FR1 — P1/high: negative conditional PUT can outlive a claimed confirmed probe cleanup

**Location:** `apps/server-storage/adapter.ts:293–315` (`verifyConditional`), and `apps/server-storage/probe.ts:46–55`. **Rule:** every dispatched unknown PUT must preserve uncertainty, and the explicit probe must not claim confirmed cleanup while an earlier PUT could still arrive (design decision 1, object-storage “Required storage operations”).

**Trigger/evidence:** the probe's negative `PutObject` request reaches the transport but loses its response before the provider executes it. `verifyConditional` never marks the operation dispatched/settled, so the error has `outcome=not_started`; `checkStorageContract` does not retain PUT uncertainty. The actual production probe/adapter, with only a synthetic HTTP service replacing the provider, returned `{"ok":false,"code":"timeout","cleanup":"confirmed"}` with zero objects after its DELETE/HEAD cleanup. Releasing the deferred request then created one `synthetic-conflict` object; its `If-None-Match: *` was correctly evaluated after cleanup when the key was absent.

**Impact/confidence:** high confidence, false cleanup assertion and leaked synthetic object under the accepted delayed-write model. A locally failed negative test is still a dispatched mutation. **Required next step:** track dispatch/conclusive settlement for every mutating probe PUT and preserve unknown cleanup status even after missing HEAD; add a production-path regression. Evidence: `storage-final-review-probe-{fixture,repro}.ts` and `storage-final-review-probe-repro.log`.

### FR2 — P2/medium: range compatibility check accepts the wrong slice

**Location:** `apps/server-storage/probe.ts:33`. **Rule:** the explicit network compatibility suite must establish exact range-read behavior for its known synthetic object (design decision 1 and object-storage “Required storage operations”).

**Trigger/evidence:** a service returns HTTP 206, the expected Content-Range and expected length, but seventeen `X` bytes for bytes 3–19. The adapter correctly enforces framing; the probe discards the returned bytes rather than comparing them with its known source slice. Actual production `checkStorageContract` returned `{"ok":true,"cleanup":"confirmed"}`.

**Impact/confidence:** high confidence, the readiness command certifies a provider whose range content is wrong. A range need not prove the whole-object hash; this probe can and should compare its known range. **Required next step:** compare the returned slice and add a wrong-content/correct-headers regression. Evidence: `storage-final-review-range-{fixture,repro}.ts` and `storage-final-review-range-repro.log`.

### FR3 — P2/medium: nonregular secret file can hang validation and server startup

**Location:** `apps/server-storage/config.ts:125–127`. **Rule:** secret paths must be regular files, and invalid storage configuration must return safe diagnostics while ordinary text startup remains usable (design configuration/startup contract).

**Trigger/evidence:** `openSync(file, "r")` opens a FIFO in blocking mode before `fstatSync` can reject it. Calling actual production `loadStorageConfiguration` with a synthetic FIFO as `NIARO_S3_SECRET_ACCESS_KEY_FILE` produced no result and required killing the child after 1,503 ms; with no writer, the open has no completion condition.

**Impact/confidence:** high confidence, an invalid mounted secret path stalls synchronous configuration loading indefinitely, including the offline checker and real server startup. **Required next step:** reject nonregular paths without blocking, preserving descriptor-based regular-file and size checks, and test it in a bounded child process. Evidence: `storage-final-review-fifo-repro.mts` and `.json` (the synthetic FIFO was removed).

### FR4 — P1/high: mutation admission inside an outer transaction is not durable before dispatch

**Location:** initial `apps/server-storage/registry.ts:40–41,132–161` (transaction helper and mutation admission). **Rule:** mutation admission must commit before asynchronous provider I/O; a later local completion check cannot undo a late remote write (accepted SR1/design persistence contract).

**Trigger/evidence:** reserve H, start an outer SQLite transaction, call production `RegisteredObjectStore.put(H)` with a paused provider port, then roll back the outer transaction. The registry helper joins the caller's transaction, so its admitted PUT token rolls back after dispatch. An explicit DELETE then retires H and replacement location activation succeeds. Releasing the delayed PUT creates data in the old location while post-I/O completion merely fails `location_mismatch`. The initial source produced `{"dispatched":true,"remoteAfterLatePut":true,"retained":0,"completionCode":"location_mismatch"}`.

**Impact/confidence:** high confidence, violation of the location/reference fence for an internal caller invoking mutations inside an outer transaction. Current startup does not itself invoke this path, but the exported production store admitted it and the shared workflow transaction boundary makes the invariant relevant. **Required next step:** refuse mutation admission inside an existing transaction before any network call, while allowing atomic reservation composition; add a real-DB regression. The coordinator first relayed this concern from the author; the review conclusion is based on independently executed code. Because the author had already added a live guard, initial registry source was extracted from `storage-final-review-initial.patch` into `storage-final-review-initial-registry.ts`, changing only its import path to the actual unchanged production types module. Evidence: `storage-final-review-transaction-initial-repro.ts` and `.log`. An intervening live probe already rejected admission with `busy`; final frozen-version inspection is still required.
