# Design

## Context

Owner decision of 2026-11-07: replace Mastra with Pi Durable (`@earendil-works/pi-durable`) as Niaro's agent core, for the simplest reliable stack: one language, one process, one database driver (`node:sqlite`), one agent core, one path to models. The NIAR-301 spike (`spikes/pi-durable/`) proved providers from runtime configuration, policy hooks (approval, service access, a hard budget around the provider) and crash recovery with a real SIGKILL. This change carries the migration in four waves; wave 1 (NIAR-302) builds the foundation without changing what members see.

## Decisions

### D1. Owner decisions (binding)

1. **Models only through Niaro.** Every Pi model request goes through Niaro's integration transport (`apps/server-integrations/transport.ts`: SSRF guard, trusted origins) and the admin model policy and roles (`packages/protocol/model-policy.ts`, providers and models from the catalog). Code never names a model.
2. **The budget ledger stays Niaro's** (`apps/server-identity/inference-budget.ts`): reserve before each model call, settle after, unknown usage keeps its hold.
3. **Recovery policy A.** After a restart an interrupted model call may be retried, counted against the budget and bounded by Pi's `restartLimit`; a process resumes; an external write is never re-run blindly: it carries an idempotency key, or the model is told it was interrupted.
4. **Exact pins.** Pi packages are pinned to exact versions; every Pi upgrade starts with a review of its changelog and API (`docs/architecture.md`).
5. **Breaking changes are allowed** (pilot): no compatibility shims for old data or builds, but existing server data must still open.
6. **Members never see internal delivery states,** and sent text never returns to the composer.

### D2. One module boundary: `apps/server-agent/pi/`

The agent core lives in `@niaro/server-agent` under `pi/`, exported as `@niaro/server-agent/pi`, beside the Mastra runtime it replaces:

| File             | Role                                                                                                                                                             |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `core.ts`        | `PiAgentCore`: one Harness over one `node:sqlite` file (created `0600`), policy A settings, the binding extension, `createConversation(scope, route)`, `close()` |
| `provider.ts`    | The Niaro Pi provider: route keys as Pi models, one call plan per request, streaming, fallback, error codes Pi can classify                                      |
| `openai-wire.ts` | Pi transcript to an OpenAI-compatible chat completions body, and the completion (streamed or not) back to a Pi assistant message with usage                      |
| `scope.ts`       | `niaro.scope` conversation document (organization, workspace, member) and the per-request binding of Pi's provider session to scope and budget run               |
| `tools.ts`       | Policy A for writes: `idempotentWriteTool` (key, replay safe) and `interruptibleWriteTool` (no key, the model is told)                                           |

The identity side is `apps/server-identity/agent-core.ts` (`agentCoreModelHost`): it turns a request's route and scope into a call plan over the catalog store, the transport and the ledger. `IdentityService.openAgentCore()` opens the core on start (beside the identity database; see D10 for the file name) and `close()` closes it before the identity database. Pi is ESM-only, so the CommonJS-scoped identity code loads it with `import()`, as it loads the Mastra runtime.

### D3. Pi models are policy routes, decided per request

A Pi model id is a route key of the model policy (`chat`, `background`, `designer`, `checker`, `selector`, `web_search`, `escalation`, `service:<id>`, `preset:<id>`), never a catalog or vendor model. For each request the host resolves the route under the workspace's policy (`ServiceCatalogStore.selectRoute`, with role defaults and tiers), so a policy change applies to the next request, and the provider and key come from the catalog. Fallback moves to the next model only after a failure that provably never left (`fallbackAfter`), never after any text was streamed. A `beforeProviderRequest` hook may change sampling but never the model: the body's model is reset to the policy's.

Pi's route models carry conservative metadata (64k context, 8k output) for Pi's compaction; the real model's limits are enforced by the ledger (`max_tokens` clamped in enforce mode).

### D4. Our own provider instead of pi-ai's adapters

`pi-durable` hard-depends on `pi-ai`, and `pi-ai` lists the SDK of every vendor it speaks (openai, anthropic, google-genai, bedrock: about 100 packages). Niaro implements Pi's `Provider` interface itself over the integration transport, speaking the OpenAI-compatible chat completions dialect that both OpenAI and OpenRouter providers use today (the body matches the current model code: temperature 0.1, no parallel tool calls, no `max_tokens` unless the ledger clamps it). The four vendor SDKs are removed with pnpm overrides (`pnpm-workspace.yaml`); pi-ai's own modules load them lazily and Niaro never loads those modules. A test asserts that the SDKs cannot be resolved and that a full Pi run never calls `fetch`. Niaro's requests carry no third-party attribution headers (`identity: { attribution: null }`).

### D5. Scope and budget run per request

Pi gives a provider only the conversation's provider session id. A `beforeRequest` hook (same task invocation, right before the request) binds that id to the conversation's `niaro.scope` document and to the budget run `pi:<conversation>:<first input of the run>`. The provider session is created with the conversation (`conversationCreated`), so the first request is bound too. A request without a complete scope is refused (`niaro_scope_missing`) before anything is sent. Because the run key is stable for one Pi run, a retry after a restart reserves against the same ledger run as the interrupted attempt. This side channel is not a Pi contract (spike risk 5); it is covered by tests and must keep the binding extension installed in every conversation (waves 2 and 3 must not narrow `agent.extensions` without it).

### D6. Budget around every request

The call plan's transport is `budgetedInferenceTransport` around the server's integration transport: reservation under the identity queue before dispatch (refusals such as `catalog_budget_exhausted` never reach the provider), `max_tokens` clamped in enforce mode, dispatch marked right before the first byte, settlement from the provider's own usage, `unknown` with the full hold on a failure after dispatch, zero for a connection that provably never left. The provider's daily request counter (`useProvider`) increments in the dispatch guard. Pi's own usage record (`pi.usage`) gets the provider's token counts and, for display, the ledger's price; the ledger stays the authority.

### D7. Recovery policy A as Pi settings

`RECOVERY_POLICY_A`: `retry` enabled with at most 2 retries (backoff from 2 s, at most 30 s) and `restartLimit` 3. A host may tighten them, never loosen them (the core takes the minimum). On open the core calls `resume()`: an interrupted model request is a failed attempt and is retried; each attempt reserves once, and the killed one keeps its hold (the ledger turns `dispatched` into `unknown` when it opens). Error text decides Pi's retry: transient failures (timeouts, connections, 429 and 5xx) read "...: model service temporarily unavailable", which matches pi-ai's retryable patterns; refusals are bare codes that match none, so they fail the run at once. Writes follow `tools.ts`: an idempotent write is re-run with the key `niaro-pi-task:<task id>` (stable across Pi's re-run, different for a model's new call), any other write gets Pi's "interrupted and may have partially run" result.

### D8. Crash harness for every wave

`tests/helpers/pi-crash.ts` starts a worker (`<worker> <scenario> start <dir>`), waits for a `MARK <name>` line, kills it with SIGKILL, then runs `<worker> <scenario> resume <dir>` and returns its `RESULT <json>` for the test to assert. Wave 1's worker (`tests/helpers/pi-crash-worker.ts`) covers a killed streamed model call and killed keyed and unkeyed writes; waves 2 and 3 add their own scenarios (approval waits, process phases, chat delivery).

### D9. Data

Wave 1 adds the agent core file (`identity.sqlite.pi.sqlite` since wave 2) in the identity directory and leaves every existing file as it is: the identity database and the Mastra store open as before. Chosen for later waves: chat histories and process checkpoints in the Mastra store are **not migrated**. Wave 3 starts new chat threads on Pi; wave 4 drops the Mastra store and removes conversation and process rows that point into it with a one-time cleanup, so an existing server still opens with its members, catalog, policies, budgets, memory and processes' definitions intact. Backup and restore learn the new file in wave 4, when the Mastra file leaves them.

### D10. Processes on Pi tasks (wave 2, NIAR-303)

A process run keeps today's call-driven contract (`NativeWorkflowInput` → waiting, succeeded or failed) and today's trusted boundary (`authorize`, `enter`, `leave`, `action`, `agent`, `reconcile`) in the identity server; only the engine under it changed. `apps/server-agent/pi/process-engine.ts`:

- **Checkpoint.** One session document per run (`niaro.process-run`, keyed by the run's workflow id: compiler, run, resource, artifact) with the frozen graph's digest, the input, the steps (node, carry before, the decision it was resumed with, status `running`/`success`/`suspended`, carry after, pending approval or question) and the result. Every change is stored as a complete revision.
- **Drives.** Each call creates one `niaro.process-segment` task (background task of the root conversation) that runs node after node, one phase per node, committing the step as `running` before the boundary call and its end after it, and ends when the run waits, succeeds or fails. The boundary lives in the request that drives the run, passed to the task by an in-memory token.
- **Restart (policy A, corrected by the owner after wave 2).** Segment tasks are `abandonOnRestart`: the boundary they called lived in the process that died. When the identity server starts again (`attachWorkflow`), `process-resumer.ts` drives every run its journal still shows `running`, exactly as the original command would, under the person's current membership and a live sign-in (the scheduled hub fill pattern). The agent core admits the restart only after `reconcile` proved every stored boundary (`proveProcessRunCheckpoint`); receipts decide whether an action already took effect, so a write is never repeated; the checkpoint counts these automatic restarts (`automaticRestarts`) and refuses a fourth (`process_restart_limit`, `RECOVERY_POLICY_A.restartLimit`). A run that cannot be proved, or whose person lost access, fails closed as before. Runs waiting for a person stay waiting.
- **Agent core per controller.** `agent-core-owner.ts` opens one core per catalog controller beside its identity database (`identity.sqlite.pi.sqlite`; in memory for `:memory:` databases), which the identity server opens at start and closes with the native runtime. The wave 1 file name `agent-core.sqlite` changed to this sibling name so tests that share a temporary directory never share a core.
- **Old data.** Runs in flight on Mastra workflow snapshots are not migrated: an original command finds no checkpoint and fails with `process_checkpoint_missing` (breaking changes allowed).
- **Not moved yet.** Agent steps still run on the Mastra native agent runtime (`NativeAgentInput`), which chat shares; both move in wave 3 (task 3.8). The contract and native test runners keep Mastra datasets as their report store until wave 4.

### D11. Wave 3 plan: the native agent contract on Pi (NIAR-304, not yet built)

Researched at the start of wave 3; the port itself is the next session's work.

- **One contract, two callers.** Chat (`mastra-domain.ts`), process agent steps (`process-agent-runtime.ts`) and the process designer (`process-design-conversation.ts`) all drive agents through `NativeAgentInput` (`apps/server-agent/runtime.ts`): a domain `session` (`prepareModel`, `allowance`, `fallback`, `invoke`, `consumeQuestionAnswer`, `finalize`, `visibleRuns`, `state.pending`, `save`), tool `definitions`, `createModel`, `onEvent`, `onDraft`. The domain logic (authority, receipts, checker, visible replies, answer receipts, budget) lives in the session and stays. The port is a Pi implementation of the runtime side: `createPiAgentRuntime(core)` with `execute`, `inspect` and the settlement proofs, swapped in where `nativeCatalogOwner(controller)` is used today.
- **Threads.** One Pi conversation per `(resourceId, threadId)`, found through a session document family (`niaro.thread`). `memoryMode: "none"` gets a fresh conversation per run.
- **Model calls.** A second Pi provider bridges to the domain's model: per request it calls `session.prepareModel()` (model, instructions, per-step context), wraps the call in `session.allowance` (provider quota, authority) and builds the model with `input.createModel(selected, guard, observer)`. That model already uses the integration transport and the budget ledger. Pi transcript and `LanguageModelV4` prompt are converted both ways, and `session.fallback` handles a call that never left. A `beforeRequest` hook sets the instructions and appends the per-step context after the history, so tools, instructions and history stay one cacheable prefix. Service actions keep reaching the provider through one stable `call_action` tool, with their schemas in that trailing context.
- **Tools.** Each definition becomes a Pi tool: `validate` before intent, `session.invoke` to execute, `onEvent` `tool-start`/`tool-end` around it. Calls to unknown or inactive tools get the same invalid-call results as today.
- **Approvals and questions.** Decided at the start of step A; see D12.
- **Answers.** An `onYield` hook calls `session.finalize`; a `repair` continues the run with the repair message, as the checker does today. The step limit is Pi's `maxTurns`. The last two steps lose their tools in `beforeRequest`, keeping today's "answer now" note. `visibleRuns` filters earlier runs' answers out of the model context, also in `beforeRequest`.
- **Proofs.** `proveSuspended`, `proveRetired`, `proveQuestionRecovery` and `isSettled` become reads of Pi state: the run's submission status, the pending memo, and whether the conversation is idle. They no longer replay Mastra snapshots.
- **Clients.** History and streaming are projected from Pi entries in place of `apps/fixture-server/conversation-history.ts`, keeping today's client protocol. Error attempts, aborted partials, harness tool results and budget errors are never sent. Drafts keep coming from the model observer.
- **Old threads.** Threads whose history lives in the Mastra store are not migrated. Until wave 4 drops that store, they stay readable through the Mastra history reader. Sending in one starts a new Pi conversation in the same thread entry, with a short system note that earlier messages are not part of the model context. This is the least confusing option: nothing a person saw disappears before the cleanup.
- **Restart.** Under policy A an interrupted chat turn may continue under the member's current authority, as processes do (`process-resumer.ts` pattern), bounded by `restartLimit`. A turn waiting for approval stays waiting.
- **Other Mastra agents.** `meeting-analysis.ts`, `profile-extraction.ts`, `widget-fill.ts`, `catalog-enrichment.ts`, `quiet-agent.ts` and `saved-memory.ts` use Mastra agents or memory for single structured calls. They move to plain Pi model calls through the same provider bridge.
- **Tests to rewrite as Pi scenarios.** `mastra-crash`, `mastra-native-fatal`, `mastra-native-fatal-crash`, `process-question-crash`, `process-owner-crash` and `process-design-conversation-crash`. Tests tied to Mastra internals also need rewriting: `native-process-questions` (child part), `mastra-history-projection`, `native-tool-validation`, `answer-streaming`, `saved-memory-native`, `mastra-loops`, `mastra-domain`.

### D12. Wave 3 step A: chat on Pi behind a switch, approvals and questions inside the tool (NIAR-304)

- **Switch.** `NIARO_AGENT_CORE=mastra|pi` (default `mastra`; also from the automatic profile environment, `administration.identity.agentCore`) chooses the runtime the chat (`createNativeCatalogRuntime`) drives. Process agent steps and the process designer stay on Mastra until a later step, whatever the switch says. `createPiAgentRuntime(core)` (`apps/server-agent/pi/native-agent.ts`) answers the same calls as the Mastra runtime (`execute`, `inspect`, `isSettled`, `proveSuspended`, `proveRetired`, `forgetThreads`, `eraseAttachmentRun`), and the contract's types and pure helpers moved to `apps/server-agent/native-contract.ts`, which loads no Mastra.
- **Approvals and questions are decided by the domain inside the tool, not pre-classified.** Whether a call needs a person is decided where it always was, in `session.invoke` (the policy, the operation receipt `awaiting_approval`, the `ask_user` question); a pre-classifying session method would duplicate that policy outside the receipts. The Pi tool's `execute` calls `session.invoke`; when it leaves `state.pending` for this call, the tool stores the pending request as a task memo `niaro.pending` (first writer wins), saves the session, tells the request it is suspended (the request returns `suspended` at once), and then waits inside `execute` for a request that resumes this call. The resuming request binds its new session to the run in memory and hands the decision (`{ resolved: true }` after `service.resolve`, or the answer) to the waiting tool, which finishes exactly as the Mastra resume did: an approval calls `session.invoke` again and the domain returns the stored receipt (the approved write already ran once in `service.resolve`, or was refused); a question returns `{ answered, answer }`. The decision document of the spike is not needed: the durable decision is the domain's receipt, and the pending memo is what the proofs read.
- **Restart.** Tools are `replay: "safe"`, because `session.invoke` is idempotent per tool call id (receipts and memory receipts answer a repeated call; an unknown write is never resent), which the Mastra resume already relied on. A tool re-run after a restart finds its `niaro.pending` memo and waits for the resume again, so a pending approval or question survives a restart with no session bound. A tool re-run that has no pending memo was cut off while it executed: it ends with an `interrupted` result (memo `niaro.started` from an earlier process), so nothing executes again without a request. A model request after a restart has no bound session and fails the run without a retry (`niaro_native_run_unbound`); continuing interrupted chat turns under policy A (process-resumer pattern) is a later step.
- **Threads.** One Pi conversation per thread (`niaro.native-thread` session documents, keyed by resource and thread). A new turn whose thread's conversation is still busy with another run's suspension forks the conversation at the entry before that run, so the waiting approval stays resumable and the chat goes on. The user input entry is `niaro.user` with the run id, which ties history segments to runs (visible replies, NIAR-263).
- **Model calls.** A second Pi provider (`niaro-native`) bridges each request to the bound session: `prepareModel` per step, `allowance` before dispatch, `fallback` after a call that never left, and `input.createModel` (the integration transport and the budget ledger, unchanged). The provider also does what the Mastra processors did: instructions and the final-step note first, the per-step context last, the `call_action` listing after the latest user message, earlier turns' calls collapsed into a note, withheld private answers, answer-only last steps, and `session.finalize` on a final answer with up to two checker repairs, so a rejected answer never reaches the transcript. Its failures are bare codes, so Pi never retries a chat request by itself; the domain classifies the failure as before.
- **History.** `inspect` projects Pi entries into today's message shape for the domain and tests. Failed attempts (`stopReason` `error`), aborted partials, harness tool results (`<harness>…`) and budget errors never appear; tool arguments are shown as `{}` and results through the same transcript filter as before. Clients read the public conversation ledger, which does not depend on the runtime, so they are unchanged.
- **Known difference.** Pi's transcript stores the tool arguments and results of a run (Mastra stored opaque copies). The model never sees earlier turns' calls (they collapse into a note), and `inspect` keeps them opaque; erasure keeps working through `forgetThreads` and `eraseAttachmentRun`, which delete the Pi conversations of a thread.

## Risks

- **Upstream churn.** Exact pins; upgrades only after a changelog and API review; the tests in `tests/pi-*.node.ts` gate them.
- **Internal states in the transcript.** Failed attempts are `error` entries, interrupted writes are error tool results, killed streams leave `aborted` partials. The member projection (wave 3) filters them; members see only answers.
- **No shared transaction with the identity database.** Receipts that must commit with the transcript move into Pi documents and memos; external writes carry keys (D7).
- **Server start depends on the agent core file.** A corrupt agent core file stops the server from starting (fail closed), like a corrupt identity database.
- **Conservative route metadata** may compact earlier than a large-context model needs; refine per route when chat moves (wave 3).

## Notes for waves 2 to 4

- **Loading Pi.** Pi's packages are ESM-only and the repository's code outside `apps/server-agent` is CommonJS under tsx: load `@niaro/server-agent/pi` (and pi-ai or pi-durable in tests) with `await import(...)`, never a static value import; `import type` is fine. Tests load in a `before()` hook (no top-level await); see `tests/pi-agent-core.node.ts`.
- **Opening conversations.** Use `PiAgentCore.createConversation(scope, route)`: it writes `niaro.scope`, and the core creates the provider session with every conversation. For a service's or a preset's route call `core.provider.route("service:<id>")` before configuring a conversation with it; after a restart, offer the routes of stored conversations again before `resume()` (open with `resume: false`, offer, then `harness.resume()`), or their next request fails with `no_model`.
- **Keep the binding extension.** A conversation whose `agent.extensions` leaves out `niaro-binding` can make no model request (`niaro_scope_missing`).
- **Budget runs.** The run key is `pi:<conversation>:<first input>`; processes pass frozen caps through `agentCoreModelHost({ caps })`. The ledger turns `dispatched` attempts into `unknown` when the identity database opens, which relies on the server lock.
- **What Pi writes into the transcript.** `pi.assistant` entries with `stopReason` `error` (failed attempts, refusals with a bare code), `aborted` partials after a kill, `pi.tool-result` errors wrapped in `<harness>…</harness>` for blocks and interruptions. The member projection shows none of them.
- **Progress persistence.** Streamed progress is stored at most about one second late (`progress.persistWithinMs`); a kill can lose that much of a partial, never a committed answer.
- **Crash scenarios.** Add a scenario to a worker like `tests/helpers/pi-crash-worker.ts` (print `MARK <name>` at the crash point, `RESULT <json>` after resuming) and assert in a `node --test` file with `crashAndResume()`. Open the core with `resume: false` in the resumed step to look at stored state before Pi runs anything.
- **Not yet decided upstream.** Pi's `afterFailedRun` stays `keep` (queued inputs wait for the next input); chat may want `continue` or `withdraw` (wave 3 decision).
