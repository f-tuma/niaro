# Design

## Context

See proposal.md for the motivation and specs/ for the required behavior. Today:

- **Saved memory** (`apps/server-identity/memory.ts`). The table `agent_memory` (L204–218) holds the following:
  - `scope`, `kind` (`preference|fact|note`) and `status` (`candidate|active|superseded|deleted`);
  - `publication`, `revision`, `expires_at`, `supersedes_id` and `lineage_id`.
  - Content, `source` and `trust` sit in an AES-256-GCM payload in the Mastra native saved-memory store (`memory-payload-crypto.ts`, `apps/server-agent/saved-memory.ts`).
  - Sources are `user_note`, `user_message` and `verified_operation` (`packages/protocol/memory.ts` L38–53).
  - Trust is `user_assertion|verified_result|model_inference`.
  - A `derived` remember path exists, which stages `candidate` with `model_inference` trust (L48–49, L708), but nothing calls it.
- **Retrieval.** `MemoryStore.search()` (L1232–1310) is lexical over the latest message: preferences always, otherwise items scoring above 0, cut at `maxItems` and `maxContextChars`. `createMemoryRuntime().context()` (`memory-runtime.ts` L92–104) frames the result as untrusted attributed data. The frame is injected in the native path (`mastra-domain.ts` L2308–2321, L3800) and in the older loop (`agent-runtime.ts` L466–470, L991).
- **Memory plugin.** It is built in (`apps/server-plugins/catalog.ts` L134–141) but not enabled by default (`registry.ts` L23 enables only `datetime`). It is checked per turn at `service.ts` L2390 and L3016. Opt-out blanks retrieval (`memory.ts` L1257).
- **No post-turn or post-publish hook, and no generic job queue.**
  - Chat replies are committed in `apps/fixture-server/engine.ts` (`message()` L655–696, `commit()` L2197).
  - Meetings publish in `MeetingStore.publishRecord()` (`meeting-store.ts` L753–819), called from `analyze()` (`meeting-processing.ts` L1094–1098).
  - `HubScheduler` (`hub-scheduler.ts`) is the tick-based pattern, with per-tick limits, backoff and a budget pause. It is wired in `service.ts` L765–778.
- **Models and billing.** The decision model (`decisions.ts`) only returns a choice and cannot write text, so extraction cannot use it. Standalone billed roots exist: `service-oauth-controller.ts` L453–469 and hub fills (`hub-fill.ts` L238). Both go through `budgetedInferenceTransport` (`inference-budget.ts` L537).
- **Meetings.** Utterances are labelled `me|others|unknown`, and `me` exists only for two-track recordings (`packages/protocol/meetings.ts` L117–127). Task owners can be `me`.
- **Microsoft.**
  - Identity sign-in keeps no Graph token (`auth-provider-bridge.ts` L63–104), and nothing on the server calls `graph.microsoft.com`.
  - A person's Microsoft 365 connection is stored sealed per workspace, service and user (`service-oauth.ts` L178–191, L275–281).
  - The hosted template asks for `Calendars.ReadWrite`, `Mail.ReadWrite` and `Mail.Send` only (`apps/server-hosting/templates/microsoft-365/definition.json`).
- **Web app.**
  - The sidebar is in `app/shell.tsx` L82–92, and its order is fixed by `docs/ui-system.md` L36 and pinned by `tests/web-app-routes.test.tsx`.
  - There is no illustration or mascot system: icons are lucide, and the only inline SVG is in the process canvas and the KPI widget.
- **Concurrent change.** NIAR-243 (`niar-243-member-memory-page`) adds the member Memory page and `forgetAll`, and modifies the requirements "Memory management API" and "Memory commands". This change does not modify those two requirements, so the two deltas archive in either order. It does reuse NIAR-243's private listing.

## Goals / Non-Goals

**Goals.**
- Observations are memory records, so they inherit encryption, retention, erasure, opt-out, the version bump that invalidates pending work, and the NIAR-243 page.
- Extraction is durable without a job queue.
- The pet is deterministic: no model, no image service.

**Non-Goals.**
- Embeddings or semantic search over observations.
- Learning from service content.
- A generic background job system.
- Mobile UI.

## Decisions

### D1. Observations use the existing encrypted saved-memory publication boundary

Add `observed {sources: ObservationSource[1..5], section, personal}` to the encrypted `MemorySourceSchema`; trust is always `model_inference`. An observation is private, active immediately, and has a strict 1–300-character statement. Allowed sections are `work|projects|tools|people|style|rhythm`. Only the learner can call `observe`; assistant memory tools and ordinary `remember`/`revise` cannot submit an observed source.

Add `origin TEXT NOT NULL DEFAULT 'explicit'` (`explicit|observed`) and `seen_at TEXT` (ISO UTC) to `agent_memory`, and `personal_things TEXT NOT NULL DEFAULT 'keep'` (`keep|drop`) to `agent_memory_preference`, using `PRAGMA table_info` migrations. Section, personal classification and provenance stay encrypted. Existing positional INSERTs must become named-column INSERTs so additive migrations preserve old data and writes. Source records use the exact encrypted/public contracts in D3a, including stable server-owned source identity; no model-supplied URL is accepted. `createdAt` is first-seen and `seenAt` is last-seen. Updates preserve first-seen across the observation lineage.

`MemoryStore.observe()` captures the actor, memory version and current active observed rows under the identity queue. It records a bounded `agent_memory_observation_stage` manifest of replacement bindings/native references, then stages and seals all replacement payloads through the actual native saved-memory store outside the queue; it does not hold SQLite open across asynchronous I/O or loop through ordinary `remember()`. Refresh also seals a replacement because expiry is authenticated associated data. One final identity transaction re-checks authority, captured version, expiry, personal preference, every target row and every source, publishes the whole batch, advances the cursor, and bumps the version once if memory changed. The learner passes the cursor advancement as a synchronous transaction checkpoint. A thrown checkpoint rolls everything back. The stage manifest holds no content. Cleanup must recognize live stage references so its orphan sweep cannot remove an in-flight envelope. On failure or startup, abandoned observed-only manifests become durable erase-pending references and are removed by native cleanup; ordinary explicit staged requests keep their current retry semantics. Refresh seals against the original item id with a fresh native reference and proposed expiry, swaps that binding only in the final transaction, and leaves the old envelope unreferenced for cleanup. Abandoned staging remains invisible and cannot later publish. Refresh preserves the observation id and increases its revision; update creates a superseding observed row. Explicit, foreign, deleted, expired and superseded targets are ignored, never adopted. Invalid output fails before publication; filtered prohibited statements produce no memory write.

The 300-active-observation cap is separate from the 2,000 explicit-memory cap. Capacity eviction erases the oldest `seen_at` lineage (stable id tie-break), including native payload and request fingerprints. Retention is from last seen. `classify` and `personalThings` are strict idempotent owner commands available with the plugin disabled or opt-out enabled. Reclassification replaces the sealed payload safely; marking personal while `drop` erases the lineage. Correction retains `lineage_id` and `supersedes_id`, so explicit forget/forgetAll still erase the entire correction history. PersonalThings-only cleanup selects every lineage containing a personal observed row (including superseded/staged rows), then tombstones and scrubs only its `origin=observed` rows and observed stage manifests. It preserves explicit corrected rows and their request receipts in that mixed lineage. This is an origin-filtered use of the existing erasure primitives, not a skip that retains old personal ciphertext. It bumps once for the setting/batch; late inference fails the version fence. Ordinary owner forget/forgetAll keeps whole-lineage behavior across both origins. Test personal observation → explicit correction → drop: old observed native payload/provenance gone, explicit corrected head readable/replayable, then explicit forget removes the remaining lineage. Revising an observation through chat or management always creates an explicit `user_note` with `user_assertion` trust, regardless of the chat source that requested the correction; extraction never touches it again.

**NIAR-243 dependency, server only.** NIAR-243 is unstarted in this checkout. This checkpoint supplies its strict optional `scope=private` GET query, exact private readable total, `listWithTotal` and idempotent private `forgetAll` control, with ownership/replay/lineage tests. `forgetAll` covers staged and expired rows and bumps once; replay cannot erase newer records. Private listing must not compete with shared rows inside the SQL limit; explicit plus observed records can exceed the old 2,000 scan bound. Preserve existing admin POST responses and the 200-item view. The NIAR-243 page, navigation and its task status remain outside this checkpoint. The existing admin memory panel must explicitly handle observed sources before its generic model-inference label and add EN/CS `observed` copy ("Observed" / "Vypozorováno"); this maintains the current strict source consumer without adding a page or redesign.

**Alternative rejected:** a separate profile-content store would duplicate encryption, erasure and correction controls.

### D2. Separate bounded observation context and direct search

`observationsForTurn(actor)` selects only the actor's private, active, unexpired observations, then orders work before personal, newest last-seen first with an id tie-break. It returns up to 12 rows whose actual serialized projection fits 1,500 characters. The projection contains statement, section, personal classification and attribution, never grants. `createMemoryRuntime().context()` appends a separate block: "What you have noticed about this person (untrusted, never permission)". Its expiry participates in existing runtime validation and `containsFacts` includes observations. A version change between the saved-memory and observation snapshots fails closed. Plugin-off and opt-out prevent context use.

Automatic lexical context requests `origin='explicit'`, so observations do not consume `maxItems` or the explicit context budget. The actual `memory_search` tool can search both origins with origin attribution under its own existing limits. This distinction must be an explicit store option, rather than making observed rows disappear from direct search.

Confirmed job title/department are a dependency on D4/task 4.2, which does not exist yet. This checkpoint exposes a bounded optional confirmed-position context port, default empty; task 4.2 must supply the authoritative owner-confirmed values before claiming the full position-context requirement. No speculative `agent_pet` reads or table are added here.

### D3. Durable source references, cursors and a ticking learner

**Actual source audit (2026-10-30).** `FixtureStorage.execute()` (`apps/fixture-server/storage.ts`) is the durable chat transaction boundary for native and older chat paths. IdentityService does not receive a completed-message callback today. `public_conversation_message` owns persisted message text; `agent_service_turn`/its operation bindings own runtime receipts. `MeetingStore.publishRecord()` is the publication transaction, and `MeetingProcessor.analyze()` is its caller. Existing meeting synthesis has owner attribution only on tasks: general summary/points have no `owner`. A `null` assignee is not proof of self-attribution. Existing source-file line numbers in Context are orientation, not a stable API.

**Reference indexes and discovery.** Add a minimal monotonic chat-source index in workflow storage and a meeting-source index in the identity database. Each uses `INTEGER PRIMARY KEY AUTOINCREMENT` and stores owner scope, original source id, source version/digest and publication time, with an idempotency key. It contains no source text or service result. New source references are inserted in the same transaction as accepted own chat messages or published meeting records; retries do not duplicate them. No historical data backfill or mailbox/document reads occur. The chat port is attached to identity by existing server HTTP wiring; it exposes only bounded owner-specific reference reads, source existence/version validation, and paged pending-owner discovery. It never exposes arbitrary workflow SQL or another person's messages. In `archiveSession()` the same transaction that copies messages to `archived-<rowid>` rebinds indexed message locators to the archive, preserving their stable source id/event sequence and message id. Ordinary archive/restore retains the same event. Existing encrypted provenance resolves through the stable source id to its current owner-scoped route; empty/reused main-chat ids are not treated as deletion. True archive deletion marks that source unavailable. A locator move during inference changes the locator revision, refuses the stale batch and retries against the archive without advancing progress or creating a duplicate event. Meeting source access uses the equivalent owner-scoped store methods.

After commit, a best-effort notification marks `agent_profile_cursor` dirty and never fails the person's command or meeting. Bounded periodic discovery (at most 100 owner descriptors, at most 4 people admitted per tick, rotating pages) repairs a missed notification or crash between the two databases. Source-reference insertion is part of the original durable transaction; a reference index failure cannot claim a committed source was indexed. No content is extracted until current memory/plugin, membership and sign-in checks succeed. Reference indexes retain minimal tombstones when sources disappear, so cursor progress stays monotonic and deleted latest rows cannot cause SQLite rowid reuse to skip later work.

**Cursor.** `agent_profile_cursor` is keyed by organization/workspace/user and records independent chat and meeting event sequences, a bounded within-source offset, dirty generation, `run_after`, last attempt and failures. It records no message text or credential. A first eligible event initializes the person; completed material advances only in the final observation transaction. Material arriving during inference retains a later dirty generation. Cursor compare-and-swap prevents competing/restarted workers from acknowledging the same snapshot; single in-flight tick and a bounded lease prevent duplicate model runs. A stale or interrupted lease expires without advancing input.

**Material builder (`profile-material.ts`).** It reads at most 100 references per source stream and emits at most 24 KiB of UTF-8 JSON, including attribution. It continues oversized sources with explicit offsets rather than advancing past unread material. Input includes:
- Only the original persisted `role=user` chat text, with result/UI/attachment fields excluded. Remove Markdown blockquotes, fenced code, inline quoted strings, HTML quote blocks and forwarded/quoted tails conservatively. Ambiguous quoted material is omitted, never promoted to the person's assertion.
- Only service/action names from that person's bound invocation receipts with `status=succeeded` and a finite `completedAt`, the existing durable proof that the invocation returned a known result after dispatch. `running` alone is not dispatch proof: preparation writes it before external I/O. Exclude failed/unknown/running, proposals, pending approvals, rejected/skipped tools and arbitrary trace labels/details; never include invocation inputs, outputs or service content. A narrow `ServiceCatalogStore` projection returns names, not whole receipts.
- Only `speaker=me` utterances in a meeting owned/recorded by the actor with `speakerChannels=self-others`. Include `owner=me` synthesis tasks only when their cited quote is located in those same eligible utterances. General summary, unknown/other speakers, voice identity numbers, unowned tasks and single-track attribution are excluded. No voiceprint/biometric inference is added.

Each material part has a server-owned evidence key. Model additions/updates/refreshes must cite one or more supplied keys; provenance is derived from these keys, never accepted from model identifiers or URLs. Before final publication, re-resolve each consumed source and compare its digest/existence under current ownership. Deletion/change during inference rejects the batch and leaves the cursor unadvanced; the retry skips tombstones safely. Existing observations survive source deletion, and read views mark the source removed without exposing titles/content or another owner. Source links are relative owner routes resolved by existing authenticated chat/meeting views.

**Model and budget.** `profile-extraction.ts` under `apps/server-agent` follows `meeting-analysis.ts`: a closed `quiet()` Mastra agent, no tools, memory or shared thread, `maxSteps:1`, no SDK/provider retries, one structured call and at most one schema-repair call. The output schema caps array counts, statements, sections and evidence references. `ProfileLearner` ticks every 60 s, admits at most 4 people, and persists at least 10 minutes between attempts. It uses `createNiaroMastraModel` and the existing `budgetedInferenceTransport` with a durable logical-attempt root `profile/<user>/<attempt_uuid>` bound to its source batch (D3b), unchanged by lease recovery, `maxModelCalls:2`, `maxTokens:40_000`, `maxCostMicros:100_000`, further reduced by workspace policy. The profile adapter requires the existing `InferenceBudgetStore.canStartModel()` before preparation and again in the held dispatch guard: only current enforce-mode policies with a matching model/provider price and feasible cap reservation are admitted. Default observe/unpriced, observe/priced and infeasible price/output ceilings defer extraction without provider dispatch or cursor/profile change; ordinary chat policy is unchanged. The existing budgeted transport still reserves, dispatches and settles the root and rejects changed policy/revisions. Full-request limits and capacity tests are in D3a. Provider max-output reservations may refuse a small cap; refusal is an ordinary deferred run, never a reason to bypass the ledger. No legacy decision-router fallback is invented when no workspace chat model exists.

A scheduled authority check follows the existing `hubAgentAccess` pattern: current organization/workspace membership, current `mobile.signedIn`, plugin/operator caps, opt-out, memory version, model/provider selection/revision and policy revision, checked before reservation, at dispatch and before publication. The learner cannot invoke native actions or approve writes. Shutdown aborts inference and drains the running tick before stores close. Failure/budget refusal preserves profile and cursor; persisted backoff uses at least 10 minutes, one hour after first failure/budget refusal and six hours after repeated failures. No content enters logs. Exact stage/cursor/lease rules are in D3a.

**Output is untrusted.** Validate the full structured envelope before use. Ignore unknown/foreign/explicit target ids. Require evidence from this input batch, reject permission/instruction-like statements, and conservatively filter normalized EN/CS prohibited-sensitive-category, credential, account/card-number patterns on both eligible snippets and proposed statements. The pattern filter is defense in depth, not a claim to recognize every semantic paraphrase; synthetic negative evaluation records its limits. Personal items are dropped when `drop`, including refresh/update attempts that would otherwise introduce personal provenance. No model response chooses actor, source link, permission, budget or model settings.

**Evaluation.** Provide about 12 EN/CS synthetic chat/meeting fixtures, expected semantic observations and forbidden outputs, plus a deterministic controlled-model logic run. A live quality run is separate and uses only the already-authorized designated development model through the normal workspace budget and transport with synthetic snippets. It must not discover/read credentials or real chats; when no such model is supplied, report live evaluation as not executed and leave that part of task 3.4 unchecked. Report expected positives, accepted positives, false positives and forbidden-item misses, rather than claiming fixture routing measures model quality.

### D3a. Exact observation/extraction contracts (MR1–MR9 remediation)

#### Stored and public source schemas

All objects are strict; identity fields use existing `IdentityId`, chat ids use existing `MessageSchema.shape.id`, meeting ids use `MeetingId`, timestamps use ISO UTC `z.iso.datetime()`, digests are exactly 64 lowercase hexadecimal characters. New stable `sourceId` values are UUIDs generated by the source index; integer AUTOINCREMENT sequences are internal cursors and never caller-selected identity.

- Encrypted `ObservationSource` is a discriminated union: chat `{type:"chat", sourceId, messageId, at, digest}` or meeting `{type:"meeting", sourceId, meetingId, at, digest}`. `at` is the original user message's `createdAt` or meeting publication time. `digest` binds the eligible original source projection before batching; it excludes mutable display title and route. A separate locator revision changes on archive relocation and participates in in-flight source validation.
- Encrypted observed source is `{type:"observed", sources:ObservationSource[1..5], section:"work"|"projects"|"tools"|"people"|"style"|"rhythm", personal:boolean}`. `MemoryPayloadSchema` enforces 1–300-character trimmed content when this source is observed, in addition to its ordinary explicit content bound. Source arrays have no removed flag or URL in ciphertext.
- Public `MemoryItem` adds `origin:"explicit"|"observed"` (default explicit for old fixtures) and `seenAt:ISO|null` (default null). Server responses always send both. Deleted items retain minimal origin/seen metadata but content/source/trust are null. Observed live items are private, `trust=model_inference`, `kind=preference` only for style and fact otherwise. First-seen is `createdAt`, preserved across observed updates; owner correction is a new explicit assertion with its own save time and null `seenAt`.
- Public source is the existing source union, with observed source entries projected as the encrypted base fields plus required `{removed:boolean, href:string|null}`. Resolve each source id only under the current actor's owner scope. Available chat href is `/chat/<encodeURIComponent(currentConversationId)>`; meeting href is `/meetings/<encodeURIComponent(meetingId)>`. A missing/unowned source yields `removed:true,href:null`, without another owner's identifiers/content. The encrypted source stays unchanged when only its locator moves or disappears. Store-only callers lacking a resolver also receive removed/null, never a fabricated route.
- Merge provenance by `(type,sourceId)`, replacing a prior entry with the newest accepted source snapshot, sort by `at` descending then type/sourceId ascending, retain the first five. `seenAt` is the server attempt's captured publication time, not a model timestamp; expiry is exactly that time plus current retention days. Refresh on the same event cannot duplicate provenance. Public observation payloads over 300 characters, unknown sections, six sources, forged href/removed fields in encrypted input and inconsistent origin/trust/scope are rejected by strict schema tests.

The existing `agent-memory/1` response also adds `personalThings:"keep"|"drop"` (default keep for fixtures) and optional nonnegative readable `total`, always sent by the server. Commands extend the existing strict workspace/request envelope: `{type:"classify",id,revision,personal:boolean}`, `{type:"personalThings",value:"keep"|"drop"}` and NIAR-243 `{type:"forgetAll",scope:"private"}`. GET accepts only the workspace target and optional `scope:"private"`. `classify` targets only an owned live observed row at its shown revision; explicit/foreign ids answer `memory_not_found`. Existing `revise` plugin/opt-out write restrictions stay; classification and personalThings remain available for privacy management when learning is off. Request-id replay never repeats mutation. Command-kind reuse always conflicts, and differing payloads conflict while a live fingerprint is present. Erasure deliberately scrubs fingerprints: an erased item receipt returns only its sanitized tombstone without comparing erased payloads or restoring content. Existing ordinary explicit replay tests remain authoritative; no fingerprint is retained to enforce a post-erasure payload comparison. Private listing/count scans owner rows in pages of 256 under a common memory-version fence, so neither shared rows nor the old 2,000 combined scan limit silently hides observations/history. Decryption stays outside the identity transaction; a changed version aborts the read.

#### Structured output and accepted operations

Required envelope is `{add:Candidate[], refresh:Refresh[], update:Update[]}` with no other keys. Each array has at most 20 entries, and total operations across all three is at most 20. Candidate is `{statement,section,personal,evidence}` where statement is trimmed 1–300 characters, section and personal match the observed source schema, and evidence is 1–5 unique keys matching `^e[1-9][0-9]{0,5}$`. Refresh is `{id,revision,evidence}`; Update is Candidate plus `{id,revision}`. Revision is a positive safe integer. No model field sets source, actor, trust, kind, expiry, seen time or URL.

Validate the whole envelope before staging. Missing/unknown evidence keys, duplicate evidence keys, repeated target ids within/across refresh/update, more than 20 total operations and nonfinite/out-of-range numeric values invalidate the batch: no observation/cursor change and ordinary failure backoff. IDs not in the supplied owned active-observed projection, or mismatched captured revisions, are ignored without exposing why. The captured workspace version/current row check still rejects a truly concurrent mutation. Statements excluded by sensitive/instruction or personalThings filtering are discarded with their operation; they never refresh an old row. Refresh of an existing personal row under drop is discarded too.

Normalize exact-match keys by NFKC, case folding and whitespace collapse. Identical normalized adds coalesce to one operation with merged evidence. An add exactly matching any active owned observed record becomes a refresh even if that record was outside the model's prior projection; explicit records are never merged. If this resolution targets a row already named by another operation, reject the conflicting envelope rather than pick an order. Model-assisted semantic refresh/update can name only the supplied projection ids/revisions; local ranking is deterministic, but semantic near-duplicate quality is measured rather than claimed infallible. Apply accepted operations by target id ascending, then new adds by normalized statement/section/personal key. A filtered/ignored/empty valid result can acknowledge the validated consumed material in a cursor-only transaction with no memory version bump. No-material/deleted-reference progress uses the same checkpoint but makes no model call.

#### Whole-request and prior-projection bounds

Keep at most 24 prior observations and 6 KiB of their actual UTF-8 JSON (`id,revision,statement,section,personal`), never truncated statements. Rank by distinct NFKC/case-folded material token overlap (tokens of at least two letters/digits, maximum 32), then `seenAt` descending and id ascending; rows that do not fit are omitted from this prompt, not erased. The server's exact-match dedup still checks all active observations. Model-assisted meaning matches are limited to that supplied candidate set and remain a stated evaluation limit.

The complete user payload, prior projection plus material plus attribution/evidence/cursor envelope, is at most 12 KiB. Material builder receives the remaining byte budget and never exceeds its separate 24 KiB outer maximum. Source streams retain unread offsets; smaller prompt allocation cannot acknowledge discarded source text. The closed agent uses `maxOutputTokens:2000`, one step and zero SDK/provider retries. The actual provider request body, including system instructions, generated structured schema, evidence and repair instruction, is at most 24 KiB UTF-8 JSON; the profile transport wrapper checks this immediately before the existing budgeted transport, with the same normal dispatch guard. It never weakens `estimatedInputTokens()` (serialized UTF-8 bytes + 1,024). Repair adds at most 256 characters of fixed schema-error guidance and does not echo raw invalid output. Both requests must pass the 24 KiB bound and the real remaining root reservation; unknown usage keeps the ordinary hold and may refuse repair.

Test at 300 maximum-length ASCII and multilingual active observations plus a maximum pending source batch, using the actual closed agent/adapter/ledger request serialization. A fitting enforce/priced tariff must dispatch a bounded request and make resumable source progress; observe modes, absent/oversized tariffs, oversized full first/repair request, exhausted remaining root and concurrent policy changes must refuse before dispatch without cursor/profile change. Test repeated ticks until long source input is covered; a full stored profile cannot itself cause a repeated unbounded prior-context request. These tests measure admission and progress, not model semantic quality or provider availability.

#### Stage, cursor and lease state

- A batch has at most 20 fresh native replacement envelopes, including refresh/update. Its stage manifest contains stage/run id, actor tuple, target/new item id, expected revision/base memory version, binding/native reference/digest, lease token, deadline and `prepared|erase_pending` state, never statement or source plaintext. One owner has at most 20 outstanding manifest entries, and all owners at most 80; cleanup must finish an older owner batch before admitting another, and capacity refusal defers unpaid work. Reclassification uses one such replacement slot under the owner's serialized mutation. Ordinary explicit staged-request replay remains unchanged.
- Cursor fields: actor tuple; `chat_after`/`meeting_after` nonnegative safe integer sequences; for each stream nullable `partial_seq` (positive, greater than after) and nonnegative safe integer `offset`; `dirty_generation`/`processed_generation` nonnegative safe integers; finite millisecond `last_attempt`, `run_after`; nonnegative integer failures capped at 2; nullable lease UUID token, positive lease generation, deadline and lease expiry. Zero offset/null partial is the initial state. Offsets count Unicode code points in the versioned eligible source projection; source ids/digests/locator revisions are revalidated before reusing offsets. If a projection changed, reset its partial offset without advancing past that source. Fully consumed or deleted events advance only that owner's sequence; deleted events contain no evidence. Alternate available streams and allow at most 100 source references/100 evidence parts per batch, so sustained chat input cannot starve meetings.
- Claim under the identity queue: compare current cursor and due state, require no live lease/stage backlog, set a new UUID token and increment lease generation, store `last_attempt=now`, `run_after>=now+600000`, deadline `now+120000` and lease expiry `now+180000`. Attempt deadline covers collection, model/repair and native preparation/publication. Abort at 120 seconds; no lease renewal. Before reservation, dispatch, staging checkpoints and publication require the same token/generation, `now<deadline` and `now<lease_expiry`. Lease loss, timeout or shutdown aborts the request and can never publish, even if remote/native I/O ignores abort and returns later.
- Another worker may reclaim only after lease expiry, with a new token/generation. Mark the old observed manifests erase-pending before cleanup; immutable new native references and final token/version checks prevent old workers from publishing. Serialize put/remove per native reference, recognize live stage refs in orphan cleanup, and sweep late orphan writes again. Restart never publishes a prepared manifest; expired/abandoned observed work is scrubbed before new admission, without rewriting ordinary explicit retry stages. A nonexpired lease after restart waits for expiry instead of claiming a second execution lease; the logical batch/root and model outcome remain bound independently under D3b.
- Success atomically publishes the accepted batch, advances exact consumed sequence/partial offsets and `processed_generation` only through the captured dirty generation, releases its own lease, and bumps memory version once only if records changed. A later dirty generation remains due. Failure before publication leaves record visibility and input progress unchanged; D3b distinguishes unpaid refusal, received result and unresolved paid response before permitting any later inference. The owning token records failures (1 then 2), one-hour first/budget backoff or six hours repeated backoff, releases/abandons only its own stage references, and never overwrites a newer owner's lease. No-op success consumes validated input and resets failures; plugin-off, opt-out and revoked owners are not admitted. Timer ticks are single-flight, at most four owners admitted per 60-second tick, including failures.

### D3b. Durable paid-batch and received-response recovery (IRR-01 / CDR-01 / STYLE-R1)

An execution lease is not a paid-attempt identity. `agent_profile_batch` stores one pending batch per actor, linked from the cursor. Its immutable `batch_id` is a SHA-256 of the actor tuple, starting stream cursor/partial offsets and the exact consumed source ids/digests/ranges; store those at most 100 content-free evidence descriptors so the same window can be rebuilt. Store its canonical input digest, prior-memory revision-set digest, current privacy generation, first-seen time, and a logical `attempt_id` UUID / `root_id=profile/<user>/<attempt_id>` before any reservation. Dirty generations, new source material, locator relocation, lease expiry, timeout, shutdown and restart never replace this paid root or silently widen the pending window. A separate lease token/generation only controls who may execute or publish it.

`agent_profile_call` has at most two rows per logical attempt, unique `(batch_id,ordinal)` with ordinal 1 (first) or 2 (schema repair), exact ledger attempt id when reserved, dispatch nonce, captured privacy generation, outcome, response digest/ciphertext/expiry and optional bounded schema outcome code. Outcome is `prepared|reserved|dispatched|received|known_rejection|unknown_response|received_erased`. A batch phase is `prepared|first_dispatched|first_received|repair_ready|repair_dispatched|final_received|committed|known_unpaid_failure|unknown_response|received_erased`. Call rows remain bound to the root even when their response content is scrubbed. Only a durably received first response classified schema-invalid can open ordinal 2; it uses the same root and normal remaining caps, never a repeated ordinal 1. Two known invalid responses exhaust this batch's automatic paid allowance; no fresh root is allocated to buy the same result again.

**One real owner and atomic boundary.** Batch/call/cursor rows and `agent_inference_run`/`agent_inference_attempt` live in the same identity SQLite database; workflow source rows are read-only during dispatch. Add an optional trusted synchronous checkpoint argument to the existing `budgetedInferenceTransport`, absent for all other callers. It supplies a synchronous identity-DB savepoint wrapper and callbacks for reservation, dispatch, received response and failure. The normal ledger still owns all admission, price/cap calculation, reserve/dispatch/settle/failure calls and model output clamp. The hook cannot select credentials, change usage, refund a hold or start network I/O itself.

1. Under the existing identity serial queue, the optional savepoint wraps normal `store.reserve()` and the matching profile `reserved` call-row binding to its returned ledger attempt id. A refusal rolls this savepoint back and creates no paid dispatch. The model-policy/membership/source/lease checks still precede admission.
2. The existing held `beforeDispatch` guard runs current authority and lease checks. Inside one synchronous savepoint commit the normal ledger's `dispatch(attemptId)` and the profile call's `dispatched` nonce/state. Release/commit that savepoint first, then call the original network `start()` exactly once while the same identity queue turn is still held. No network call starts inside an uncommitted transaction. A marker/savepoint failure prevents `start`; a crash after commit but before start is conservatively unresolved, not permission to infer again. No cross-database atomicity is claimed.
3. On provider return, the normal transport computes raw usage before parsing/abort checks as today. A synchronous savepoint commits normal `settle()` plus the profile's bounded encrypted received-response checkpoint/outcome together, before the response returns to the closed agent/SDK for schema validation. A checkpoint/storage failure rolls the pair back; the normal failure path retains the dispatched hold and the profile marks unresolved. On transport throw, normal `failed()` and the profile failure outcome commit together. Other callers, including streaming/native/chat, retain their current path when the optional hook is absent.
4. Provide a narrow internal owner-checked ledger attempt-state lookup (run target + attempt id → current status) for profile restart/lease recovery. It exposes no prompt/body/key and changes no ledger state/policy. Startup already turns undispatched reservations cancelled and dispatched attempts unknown. The profile compares its bound call ids with those real statuses; it never infers nonexecution from an expired lease or a missing local response. A stale still-reserved call may be cancelled through existing `failed()` only while the identity queue proves its old lease/deadline can no longer dispatch. No new provider-status query or reconciliation endpoint is introduced.

**Bounded private checkpoint.** The response checkpoint contains only status and the received completion body needed by the existing model parser, not request headers/keys/prompts. Maximum 32 KiB plaintext per call, at most two encrypted checkpoints per pending owner batch. Seal it with AES-256-GCM using a distinct HKDF domain `profile-response-checkpoint/v1` from the existing identity secret; associated data binds actor, batch, attempt/root, call ordinal/ledger id, input digest, privacy generation and expiry. Store ciphertext in the profile call row, never plaintext or a second published-memory record. Retain at most `min(24 hours,retentionDays)` from receipt; expired/erased ciphertext is scrubbed while outcome/root/hold metadata remains. Oversized/malformed received completion is a known invalid result, not a usable checkpoint, and can use only its one same-root schema repair if admitted. An output checkpoint is always untrusted and must pass the same strict schema/evidence/credential/sensitive/personal filters before observation staging.

| Durable evidence | Next automatic action |
| --- | --- |
| Proven refusal before reservation/dispatch; or all bound attempts positively cancelled before dispatch | Keep source progress pending and back off. A later claim may retry unpaid admission. Only a positive owner-checked ledger proof that no call dispatched permits replacing an incompatible unpaid root/input plan; keep old cancelled ledger metadata. |
| Valid received response checkpoint, including response with missing/invalid usage | Reuse that response without a new provider request. Retain the ledger's unknown-usage upper hold. Fresh actor/plugin/model/policy/source/lease/version checks and a matching current input/prior-memory digest are required before publication. Unknown usage alone is not an unknown response. |
| Known received first response with schema-invalid output | Persist `repair_ready`; at most one distinct schema-repair call on the same root, including after restart, under ordinary remaining headroom. Never resend the first call. A refused repair remains pending on that root. |
| Dispatched/unknown ledger status with no durable received response; 408/504/524 without a recoverable completion; crash/lost checkpoint; post-dispatch throw; ignored-abort response not safely checkpointed | Persist `unknown_response`, retain source window/root/hold and make no new automatic provider call or replacement root. Backoff, restart, lease reclaim, dirty input and source movement cannot clear it. Other owners continue. |
| Response cache expires/is erased, owner/privacy/source invalidation prevents replay, or both paid ordinals are exhausted without a usable final result | Scrub content, preserve paid binding/outcome and any hold; do not buy the same batch again under a new root. Leave input pending and report only a bounded status code. This checkpoint has no automatic reconciliation/reset facility; explicit proof-gated recovery remains an acknowledged operational limitation. |

A genuinely received late completion can be checkpointed as positive response evidence only for its still-bound ledger call and unchanged privacy generation; this does not revive the expired worker's lease or publish observations. Usage settlement still follows the normal ledger and its retained hold; no unknown charge is cleared. A later fresh lease can reuse a valid checkpoint after all current fences and input digests match. Any own-memory correction/erasure/opt-out/personal-filter change increments the actor's privacy generation and scrubs affected pending response ciphertext in the same identity mutation boundary. Source deletion or authority revocation refuses replay and scrubs cached content. Late callbacks with an older privacy generation cannot recreate scrubbed ciphertext. A newly captured current memory version may be used only after a fresh read proves the complete owner input/prior-memory revision-set digest is unchanged; a changed owner input cannot be hidden by replacing the version. Publication atomically marks the batch committed with observation/cursor changes; only then may a disjoint next source batch acquire a new paid root. Erasure/replay never exposes checkpoint content.

**Controlled production oracles.** Use the actual learner/cursor/profile adapter plus the real budget transport, never a budget-refusal stub alone. Inject dispatched 504 and post-dispatch exception; kill/reopen after dispatch before result/stage; kill after received checkpoint before publication; advance beyond 120-second deadline, 180-second lease and repeated one-/six-hour backoffs; add dirty input and relocate sources; return a non-cooperative response late. Assert one provider dispatch for unresolved work, unchanged source progress/profile, unchanged original root and unknown hold, and no stale publication. At actual `start()` inspect a second SQLite connection to prove both markers committed; force checkpoint transaction failure and prove network never starts. Separately test known unpaid refusal retry, valid result with missing usage committing under the original held reservation without a repeated call, first known invalid response plus one same-root repair, replay of received checkpoint without inference, privacy erasure/cache expiry preserving paid binding/no new charge, and late callbacks failing the privacy generation. Also run a no-hook default-caller regression on the same real ledger after injected profile hook failures: ordinary observe/unpriced admission, priced clamp/usage and normal dispatch/accounting remain unchanged, with no leaked SQLite transaction. Keep the existing inference-budget suite green. State the measured/live limits separately; this is a profile-specific checkpoint over existing owners, not a new agent engine or ledger reconciliation implementation.

### D4. Pet data and API

**Table.** A new `agent_pet (organization_id, workspace_id, user_id, name, colour, shape, job_title, department, position_revision, revision, created_at, updated_at)`, where `shape` is `auto` or a pinned shape key. Its key is the person in the workspace, and the row is created lazily on the first GET.

**Route.** `GET|POST /admin/api/identity/pet`, in the style of the memory route:
- `workspaceActor()`, with the operator session refused;
- a strict `work-pet/1` view;
- an idempotent `requestId` per command, stored in `agent_pet_request`;
- audit entries `pet.changed` and `pet.position_changed`, without values.

**Derived data.** The stage, the look and the greeting are computed on the server from the observation list and the pet row, by pure functions in `apps/server-identity/work-pet.ts`, so web tests and server tests share the same oracle.
- **Look:** for each section with work observations, a droplet weight `min(1, sqrt(count) / sqrt(12))`; the automatic shape is the shape assigned to the section with the most work observations (ties: the most recently seen), and `circle` with none. The client gets only these numbers, never statements, so the renderer cannot leak content.
- **Greeting:** templates per language, filled with the pet's name and the statement of the newest work observation from the last 7 days.

**Personal things setting.** It is stored with the memory preferences (`agent_memory_preference` gains a `personal_things` column) and changed through the memory command `personalThings`. It applies to all memory; the pet only renders it.

### D5. Microsoft 365 suggestion

**The call.**
- **When:** on GET of the pet, at most once per person per 24 h. The result is cached in the pet row as `suggestion_title`, `suggestion_department` and `suggested_at`.
- **What:** the server finds the person's active Microsoft connection of the workspace's Microsoft 365 hosted service and calls `GET https://graph.microsoft.com/v1.0/me?$select=jobTitle,department` with that connection's access token. It uses the existing token refresh and the hosting transport rules (HTTPS only, timeout, size cap).
- **Failure:** it means no suggestion, never an error on the page.

**Scope.** The template's sign-in scopes gain `User.Read`. People connected before this change get a suggestion only after they sign in to Microsoft 365 again. The page says nothing about it, because the suggestion is optional.

**Alternative rejected: an MCP tool of the hosted server.** The `calendar,mail` preset does not include one, and widening the preset would expose user-directory tools to the agent.

**Alternative rejected: the identity sign-in token.** It is stripped, and keeping it would retain a credential the identity layer deliberately drops.

### D6. Pet artwork: one liquid shader

A live prototype is published as an artifact (`niaro-pet.html`, "Niaro Pet Prototype"); this decision follows it.

- **Renderer.** One WebGL 1 fragment shader on a single full-screen triangle, raymarching a signed distance field, in the style of the existing `VoiceOrb` liquid shader (`packages/ui/liquid-shader.ts`). There is no 3D library and no asset download. The shader source and the component together are a few kilobytes. It lives in `packages/ui` (`pet-shader.ts`, `PetView.web.tsx`), so a native screen can reuse it through `expo-gl` later.
- **Body.** The body is a 2D silhouette inflated into a soft 3D pillow: a rounded extrusion whose edge radius is close to the body radius. The silhouette is one parametric family after the Material 3 shapes, `r(θ) = R·(1 + a·cos(nθ + φ))`, with an optional stretch. That gives 8 named shapes: circle, pill, cookie (9 lobes), sunny (8), flower (6), clover (4), burst (12) and pebble (3). The lobes fade toward the centre, where the angle is undefined. Because every shape belongs to the same family, a change of shape is a smooth cross-fade of the lobe terms over about 0.6 s, never a jump between unrelated geometry. This is what keeps it from becoming "a chaos of shapes".
- **Automatic shape.** Each section maps to one shape (Work → cookie, Projects → flower, Tools → sunny, People → clover, Style → burst, Rhythm → pill). With the shape set to automatic, the pet takes the shape of its strongest section, so it changes by itself as the profile changes.
- **Water, not plastic.** What reads as premium glass or water is mostly that the body visibly bends what is behind it. A transparent blend over the page reads as film. So the canvas draws its own small studio and refracts it:
  - **Studio.** A wall with a soft spotlight and a floor below a gentle horizon, with a contact shadow and a tinted caustic. It fades to exactly the card colour (read from CSS) at the canvas edge, so the canvas is opaque yet invisible.
  - **Refraction.** The view ray refracts in (IOR 1.33), is marched to the far surface for the thickness, and refracts out to hit the wall. Each colour channel uses a slightly different IOR (1.31, 1.33 and 1.355), which gives a faint dispersion rainbow at the rims.
  - **Absorption.** The body colour comes from absorption by thickness (Beer–Lambert), so the edges are clear and the middle is deeper.
  - **Studio reflections.** A large soft key softbox upper left and a strip light on the right are reflected with Schlick Fresnel (F0 0.02). They are kept subtle, as an undertone rather than a feature: about a third of a product-shot intensity, with soft edges. Light bouncing inside the water uses a blurred version of the same studio, so inner reflections never look like shards.
  - **Translucency.** A back light glows through thin parts: a view-dependent term distorted by the normal and attenuated by thickness (Barré-Brisebois, GDC 2011).
  - **Colour pipeline.** Lighting is computed in linear space. A highlight shoulder leaves the mid-tones untouched, so the studio matches the card, while bright reflections roll off instead of clipping. A slight saturation lift follows, then sRGB.
  - **Anti-aliasing.** Pixels that the surface only grazes are shaded at the closest point and blended by coverage, so the silhouette is smooth at 1.5× DPR.
- **Surface tension.** Three slow waves (3, 5 and 7 per turn) travel round the rim, strongest at the edge and fading toward the face, with an amplitude of about 0.4% of the radius, so it is barely noticeable. They ripple harder for a moment when something new is learned or the shape changes, and are calm when the pet sleeps. The liquid then reads as held together rather than solid.
- **Following the pointer.** The body leans toward the pointer by at most about 9° sideways and 7° vertically, and the eyes look toward it by a few hundredths of the radius, eased over about 0.3 s. It returns to rest when the pointer leaves or stays still for 3 s, while asleep, and always under reduced motion.
- **Inside.** Each section with work observations is a soft Gaussian cloud of dye suspended in the water, in the section's fixed colour, with a radius from the server's weight. The clouds slowly orbit inside the body. They are integrated only along the part of the view ray inside the water, and faded near the surface, so their colour always stays inside. They absorb the transmitted light (subtractive, like ink) and scatter a little of their own colour, so overlapping clouds blend like ink in water.
- **Surface and face.**
  - The surface is the person's body colour, with diffuse light, a Fresnel rim and two specular highlights.
  - The eyes sit on the surface, drawn over the reflections, so they stay clear and expressive. They are dark, slightly tinted by the body colour, with only a faint glint and faint light at their bottom. They have soft, faintly wobbling rims, light gathered at their bottom and a small glint, and they blink. The cheeks are a faint pink absorption. Asleep, the eyes become closed arcs and the pet breathes slowly. The face follows the body's squash and tilt.
  - No stage adds an exterior glow or halo. User refinement on 2026-10-30: the maximum-stage backlight was distracting; retain only the body’s own glass highlights and internal colours.
- **Motion.**
  - Breathing (squash and bob), a blink about every 4 s, droplet orbits, and a short squash "pulse" when a new observation arrives (a growing section weight).
  - At most 30 frames per second.
  - Rendering stops when the canvas is off screen (`IntersectionObserver`) or the tab is hidden.
  - Under `prefers-reduced-motion`, there is one still frame.
- **Resolution.** The canvas is the CSS size × min(DPR, 1.5), capped at 480 px.
- **Fallback.** Without WebGL, or when the shader fails to compile, the page shows a still SVG: the silhouette path from the same formula with blurred droplet circles, in the same colours.
- **Small sizes.** The sidebar icon uses that static SVG, never a second WebGL context.
- **Colours.**
  - 8 body tints and the 6 section colours become UI tokens, checked in light and dark.
  - Eye and outline colours meet 3:1 contrast against both page backgrounds.
- **Accessibility.**
  - The canvas has `role="img"` with a label naming the pet, its stage, whether it sleeps and the sections it knows.
  - All information shown by the pet also exists as text on the page.

*Alternatives.*
- **Three.js with marching cubes:** about 150 kB gzip plus mesh work every frame, for the same look.
- **Lottie or a hand-drawn illustration set:** it needs an illustrator for every shape × stage, and it cannot morph continuously or follow the profile.
- **SVG with a gooey filter:** it is kept only as the fallback, since it has no depth or refraction.

### D6b. Expressions, touch and weather

The prototype shows these as well (version 9 of the prototype artifact).

- **Expressions.** Expressions come from the shape of the eyes and mouth, never from icon swaps (as in Slime Rancher; animators shape emotion with the lids).
  - **Parameters.** The face is driven by nine numbers: eye height, upper lid (open to shut), lower lid (rising into a smiling crescent), lid tilt (inner corners up for sad or worried), love sparkle, left-eye wink, smile (−1 to 1), mouth open and blush. Named faces are presets of these numbers, and the renderer eases toward the current preset.
  - **Eyes.** Each eye is a glossy black bead with its own sphere-like normal. It reflects the same studio as the body, so its highlight matches the scene. It has a crisp catchlight, a little bounce light in its lower edge, and a soft socket shadow around it. A shut eye becomes a curved lid line.
  - **Mouth.** Closed, the mouth is a tapered crescent, thicker in the middle. Open, it is a cavity: dark at the top, with a softly lit tongue and a faint lip rim.
  - **Opacity.** All features are opaque and drawn over the reflections, so they read with full contrast.
- **Touch.**
  - A pointer-down triggers a squish, a lean away from the touch, and the next reaction in a cycle: happy, giggle, surprise, wink, love. Six quick taps trigger a giggle, and a tap while asleep makes the pet stir.
  - Each reaction shows **one sign above the head**, like an anime emote (manpu): sparkles, notes, an exclamation mark, hearts, a sweat drop, "zz" or "…".
  - The sign is not a floating icon. It is a signed-distance glyph rendered as a small piece of the same water: a rounded bevel, the studio refracted through it, a light tint per sign and the studio reflection. It pops in with a slight overshoot and fades after about 1.4 s.
  - Reactions are client-only state.
- **Idle.** About every 9–16 s the pet looks to one side, or yawns at night or in fog. There is no idle behaviour under reduced motion.
- **Weather.**
  - **Source.** The server keeps one weather state per workspace: one of `sun`, `rain`, `snow`, `storm`, `fog`, or none. It comes from an optional workspace location (a city with its coordinates) set by an administrator, and is fetched from Open-Meteo (free, no key; the data is CC BY 4.0) at most every 30 minutes for all people of the workspace. Only the workspace coordinates leave the server, never anything about a person. There is no browser geolocation.
  - **Night.** It comes from the person's time zone and the sun times at the location; without a location, 20:00–07:00.
  - **Effects.** The client maps the state to a light mood (warm or cool key light, night dimming, lightning flashes for a storm), overlay particles (rain streaks, snow, motes in the sun, twinkling stars at night, drifting fog) and the resting face. With no weather and day, the render is identical to the plain pet.
  - **Lines.** The greeting gains one weather line.

### Invariants

- An observation is never shared, never readable by another person, and never a permission. Extraction writes only `observed` rows of the person it runs for.
- Extraction never reads service results or other speakers. The material builder is the only input, and it is tested.
- An erased observation's content is not returned anywhere, including in the pet's look, the greeting and replays.
- The job title and department never reach an authorization path; they are passed only to prompt context and the pet view.

## Risks / Trade-offs

- **[Model extracts junk or near-duplicates.]** The existing observations are given to the model with refresh and update instructions, the cap is 300 with eviction by staleness, and the person can delete or correct. Extraction quality is measured on a small fixture set (task 3.4).
- **[Sensitive category slips through.]** The prompt rule, the server pattern check for credentials, owner-only visibility and one-click delete reduce the risk but do not remove it. Conservative EN/CS sensitive-category patterns add defense in depth; they cannot establish semantic completeness for all paraphrases, which remains an evaluation limit.
- **[Cost per active person.]** At most one extraction attempt per 10 minutes per person, only after new material, as a ledger root under workspace caps. Twenty people yield at most 120 attempts/hour and up to 240 model calls/hour if each attempt needs one schema repair; budget refusals and backoff can reduce these bounds.
- **[Memory plugin is off by default.]** Without it, pets stay asleep. The pilot needs the operator to allowlist memory. The deployment guide gets a note.
- **[NIAR-243 not merged first.]** This server checkpoint supplies the private listing/control dependency; NIAR-243 stays unstarted and its member page/no-session UI rule lands separately. The later Pet page still needs that no-session rule.

## Migration Plan

- **Schema:** additive columns on `agent_memory` and `agent_memory_preference`, and new tables `agent_profile_cursor`, `agent_memory_observation_stage` and minimal source-reference indexes; later pet tasks add `agent_pet` and `agent_pet_request`. Existing rows get `origin='explicit'`.
- **Microsoft 365:** the template change adds a scope and needs no data migration.
- **Rollback restriction:** in-place downgrade to the prior binary is unsupported. Its positional inserts have the wrong column count after migration and its strict decrypted-source decoder rejects observed envelopes. Additive migration means old explicit data remains readable/writable by the upgraded build, not that the old binary accepts the new format. Prefer a forward fix. An operator choosing recovery must stop all writers and restore a consistent pre-upgrade backup of identity, native saved-memory and workflow stores; that loses subsequent writes. No coercion of observations into user assertions or untested reverse migration is offered. Compatibility evidence must populate an old-format store with encrypted explicit memory/preferences, reopen/migrate with the new build, read/write/revise/toggle preferences and add/read an observed envelope. A documented schema/decoder incompatibility probe must show why direct old-binary downgrade is excluded; this is not a tested restore/deployment claim.
