# ADR 019 — Generated UI in answers with OpenUI Lang

Date: 2026-10-23. Status: implemented; live-model use measured on 2026-10-24 for one model (see [agent trust](../agent-trust.md#explicit-live-model-mode)).

## Context

ADR 017 let the model compose cards through a `compose_card` tool: a flat JSON node graph validated by our own schema and drawn by our own renderers. The vocabulary was small (fields, lists, notices, simple forms), had no tables or charts, cost an extra model step per card, and lost its content in history because tool arguments are not kept there. The owner wants a wide range of UI that complements answers and visualises results on the phone and in the web app.

## Decision

Replace model-composed cards with [OpenUI](https://www.openui.com) (MIT): the model writes an OpenUI Lang program for the visual part of its answer, and our clients render it with our own component library.

- **Transport.** One program in an ` ```openui-lang ` fence after the Markdown text, OpenUI's inline mode for chat. The program streams with the reply, stays in the model's history as its own text (an answer built on private service data is withheld from later turns, as before), and needs no tool call.
- **No cloud.** Instructions are generated by lang-core's `generateSystemPrompt` in local mode from our spec; models stay on our provider catalog. No Gateway, Autofix or telemetry: install and runtime telemetry are disabled and the CDN-loaded devtools package is removed.
- **One spec.** `packages/openui-library/spec.ts` defines names, positional arguments and limits once; the server validator and both renderers use it.
- **Server admission.** Before a program is stored or delivered, lang-core's parser and our checks drop unknown or misplaced components and unsafe controls, and refuse data fetching (`Query`, `Mutation`) and oversized programs. Actions are limited to `@ToAssistant` (fills the message box; the person sends it), checked http(s) `@OpenUrl`, and local `@Set`/`@Reset`.
- **Storage.** The normalized program is a separate, negotiated `ui` field on the assistant message (`ui=agent-openui/1`), so it can sit beside a service result and older clients keep the text.
- **Renderers.** The web uses react-lang's `Renderer` with shadcn components. react-lang 1.0.1 renders DOM elements, so the phone has a renderer built on lang-core's parser and evaluator with React Native components.

System UI (approvals, questions with options, sign-in, process offers, hub widgets) is unchanged. The server's deterministic passive cards for service results and work summaries stay on `agent-card/1`.

## Consequences

A new kind of visual needs a component in the spec and both renderers; a new arrangement needs nothing. Model text in the UI is still untrusted: admission bounds its shape and actions, and the consistency checker judges its claims with the reply, but neither proves factual truth. Follow-up buttons never act on their own, so a write keeps its explicit approval.

Stored model-composed cards show their text. `card.respond` still resolves a form of such a stored card for older app builds; it is not produced any more and can be removed with the internal card origin of process starts.

Chat answers are published once complete (after the checker), so streaming renders progressively only when a streaming transport is added; the renderers already accept partial input. Live-model evaluation of when and how the model uses UI remains open.
