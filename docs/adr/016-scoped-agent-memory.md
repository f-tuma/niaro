# ADR 016 — Scoped working context and explicit long-term memory

Date: 2026-09-30. Status: accepted for the model planner (`agent-1`).

The explicit intent, scope, trust and lifecycle policy below also applies to
native Mastra execution. The October 7 payload storage, asynchronous publication
and erasure implementation is superseded by [ADR 018](018-native-saved-memory-and-conversation-identity.md).
In particular, canonical saved payloads now belong to encrypted Mastra Memory;
native I/O runs outside the identity queue and exact erased-request recovery can
finish pending native cleanup. The original implementation details below are
the September 30 checkpoint, rather than a description of a second active store.

The agent loop previously carried a paused task across a new chat session, lost useful read results after a completed lookup, and reused old results without checking source access. A display transcript is insufficient for reliable continuation. Long-term memory also needs a separate identity, lifecycle and trust boundary.

## Decision

The server owns a typed working context: conversation ID, original goal, opening time, clarification and successful read receipts. A new session starts fresh. Same-session continuation requires a current visible result or question, a nonnegative age within 30 minutes, and current source access, revisions and policy. A configured Jev checker distinguishes an answer to a paused question from an unrelated request. No checker means starting a fresh task. Reads are projected again from authoritative receipts before inference; only successful reads become action dependencies. Writes and failed reads cannot poison a later independent read.

The server journals each bounded assistant tool-call batch before execution, gives actions stable IDs, and repairs missing tool results from saved plans/receipts. Every assistant call has a paired result before the next inference, including deferred calls after an approval. Replay returns the recorded outcome and never dispatches a completed action again. An identical rejected write remains rejected; changing the proposed parameters requires a new check. Model output never supplies authorization.

Long-term memory is a statically shipped internal plugin, `memory`, alongside `datetime`. It is disabled by the operator allowlist by default. It runs inside the authenticated identity runtime, rather than the pure datetime executor, and offers `memory_search`, `memory_remember`, `memory_revise` and `memory_forget`. No remote plugin code is loaded.

Records belong to an organization, workspace and user. Private records are accessible only to that user; optional workspace records are visible to members and managed by owners/admins. Records have a kind, status, revision, source, trust and expiry. Explicit manual notes and exact authenticated chat instructions are user assertions. Derived content remains a candidate and does not enter the model context. An operation-derived fact requires a currently authorized successful read receipt, the pinned service and a 30-minute source lifetime. This release does not automatically extract or promote facts from chat archives or service results.

Retrieval is bounded by item and character budgets. Preferences take priority; other facts and notes use lexical relevance. Memory is framed as attributed untrusted data and cannot grant permission, change instructions or replace a current service check. The runtime persists only its version, earliest expiry and verified source references with a pending proposal, not a second copy of retrieved memory content. It checks them again inside the dispatch queue, including after restart. Deletion, revision, opt-out or lost source access invalidates a pending context. Conservatively, any memory change in the workspace advances its version, including a different user's private change.

Corrections supersede one identified record with a new revision lineage. Chat corrections require the entire latest authenticated user message to specify the exact old and replacement content as two JSON strings: `Oprav paměť: "OLD" na "NEW"` or `Revise memory: "OLD" to "NEW"`. `→` and `->` separators and optional initial `Prosím` / `Please` are supported. Decoded content is not case-folded or trimmed; empty values, edge whitespace, identical values and trailing instructions are rejected. The strict tool takes only `id`, expected `revision` and replacement `content`. Inside the mutation transaction, the server checks that the record is active, private, belongs to the current actor and matches the exact old content. A stale revision conflicts. Multiple currently retrievable active private records with the same exact old content are ambiguous and require selection in the console. The ambiguity check applies current source access, verified-source lifetime and record expiry atomically, so expired or revoked duplicates do not block correction. The replacement retains the record kind, receives `user_message` provenance from the trusted command and is a user assertion. Shared or candidate records require the existing console management flow.

For chat correction, the memory mutation, request receipt and projected agent tool receipt are saved in one identity database transaction. The journal projection pairs the corrected call and skips the remaining calls in its model batch, clears pending work and the old memory pins, and leaves the live turn unchanged until commit. A failed synchronous checkpoint rolls the mutation and journal back together. Recovery after commit starts from the paired receipt with fresh memory rather than retrying stale arguments against the new memory version. This guarantee covers the correction checkpoint; it does not claim that every memory mutation uses this path or that a physical process crash has been tested.

The correction receipt fingerprint binds the old content, record ID, revision, replacement and trusted provenance, so retry cannot revise a different record or accept altered arguments. Forgetting erases content and provenance throughout the lineage, including idempotency fingerprints, leaving minimal tombstones so retries cannot resurrect it. A replay after erasure returns only deleted metadata. Audit entries contain action and scope, without memory payloads. Forgetting saved memory does not erase the original chat or independent service receipts. Expired records are excluded from reads immediately. An explicit maintenance operation scrubs expired payloads at startup and hourly inside the identity queue; reads and replay never perform cleanup. Backup erasure remains separate operator work.

## Consequences and next work

The first plugin is intentionally explicit and inspectable. Chat saves require the latest user message to start with `Remember …` / `Zapamatuj si: …`, with the tool copying that exact content. Chat erasure requires `Forget …` / `Zapomeň na …` followed by the exact saved content. Chat correction requires the explicit two-value instruction above; ordinary saves remain additive, without silent semantic deduplication or inferred replacement of an opposite assertion. The console supports correction and erasure by ID. Per-user opt-out disables retrieval and new writes while retaining inspection and erasure.

The schema provides configurable retention (for new records), context length, record count and shared scope. Explicit operator memory settings cap workspace overrides; omitted operator settings allow configuration within the protocol bounds. Lowering a cap takes effect on retrieval even when a saved workspace override is larger.

Trustworthy behavior still needs evaluation with real models: calibrated uncertainty, changed-topic detection, retrieval recall, stale fact handling and tool-injection resistance. The [repeatable scenario runner](../agent-trust.md) measures the current loop's mechanics using scripted inference; it does not grade a live model. Next work includes durable suspend/resume of multiple goals, real-model evaluation and a separate extraction pipeline that produces reviewable candidates. This design supplies durable state, evidence and control; it does not establish consciousness or prove reliable behavior for every model.

## Validation

`tests/service-catalog.node.ts` exercises session isolation, follow-up results, source expiry/revocation, backward clocks, checker rejection, independent reads, interrupted tool batches, receipts and memory invalidation. `tests/memory.node.ts` covers scope, trust, lifecycle, revisions, erasure and checkpoint rollback. `tests/memory-runtime.node.ts` covers exact correction syntax, authorization, stale and forged revisions, bound retry, erasure, currently retrievable duplicates and proposal metadata. `tests/memory-http.node.ts` covers authenticated management and plugin constraints. `tests/memory-chat.node.ts` verifies the complete identity-to-model integration across new sessions, opt-out and deletion during inference. `tests/agent-trust/memory-scenarios.ts` checks explicit correction through the actual loop, restart, malicious or ambiguous requests, interruption before and after the correction checkpoint, and approval invalidation after a correction. Tests use synthetic providers and do not require paid inference or live service writes.
